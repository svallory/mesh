# Porting Hyper to Mesh: what the entity files leave out

The entity files in `src/domain/` hold what Mesh builds today: attributes, keys, relationships, the actions with their checks and steps, and, since M5, every effect a command has inside its own aggregate (`actions` and `tx` in a `run` step, `run [after=:write]`). The effects that reach another aggregate, the `warnings` and the late result are plain TypeScript functions in `src/domain/<module>/<module>.commands.ts`, each one application transaction (`transaction(fn, context)` from `#mesh`). They follow the Hyper specification (`svallory/hyper-engine-spec`, branch `feat/protocol-phases`, commit `ccc00f9`: `PROTOCOL.md` and `schemas/protocol.ts`) and nothing else, as [ADR-0072](../../apps/docs/docs/architecture/decisions/0072-mesh-1-0-is-the-port-gate.md) requires; the five execution entities (Run, Attempt, Invocation, Machine, SessionReference) are not in the spec's twelve and follow the drafts in `notes/hyper-port/entities/`. Every read is the auto read: a caller's `{ filter, sort, limit, offset }` serves Hyper's `get_*`, `list_*` and `list_events`, so those reads are not omissions.

Each line names the entity, the construct left out, its code in the [gap analysis](../../apps/docs/docs/architecture/research/hyper-port-gap-analysis.md) (`G` for a gap, `D` for a draft finding), and the milestone of [roadmap revision 5](../../apps/docs/docs/architecture/roadmap/roadmap.md) that delivers it. "No gap code" marks a limit the analysis does not list.

- All entities: one rule reused by name across actions and entities, so each check is repeated (G04): after 1.0.
- All entities: policies, with the actor's role read through `tx` inside the transaction; Hyper's `role` rule (`canWork(actor)`, `memberships/rules.ex:12-17`) is one, so `test/rules.test.ts` lists it as not ported, and so are the denials `claim.holder` (only the holder renews or releases, `tasks/claim.ex:120`; the spec also answers it for an unfenced `task.complete` while someone else holds the claim and for a submit by someone who never held one, `PROTOCOL.md:249`, `:326`, where the port answers `claim.current-fence`, as the failing case of `claim.current-fence` in `test/rules.test.ts` pins) and `review.reviewer` (only the Task's reviewer reviews, `tasks/review/checks/reviewer.ex:21`), which are not among the 57 rules (G21, G22): M8.
- All entities: a `system` context key so internal and nested writes pass authorization; until then the actions only the effects call (Claim `end`, Task `touch`, Submission `recordAccepted` and `settle`, Assignment `start` and `finish`, Completion `record`, Run `settle`, LateResult `record`) are exported and any caller can run them, and the Task's version does not move (G20): M8.
- All entities: a read's `load` input (the roadmap has no milestone for it); the `load` step of an action works, and `loadTaskFields(tx, rows, names)` and its siblings load a relationship or computed field inside a transaction (no gap code): not scheduled.
- All entities: filtering or sorting a read by a rollup or computed field (`maxFence`, `derivedState`) fails with an error that names M10 (G07): M10.
- All entities: the plugin hook points and blocking-condition providers; Task's `task.not-blocked` rule asks the providers (`tasks/task/rules.ex:82-88`), so `test/rules.test.ts` lists it as not ported (G11, G31): M6.
- All entities: microsecond timestamps; Mesh stores milliseconds (G24): not scheduled.
- All entities: an id in a required relationship that names no row fails with a `FrameworkError` when the action loads the relationship (and is stored as given when nothing reads it, SQLite having no foreign keys), where the spec answers `not_found` in the permission phase (PROTOCOL.md §4.4); `attempt.session` and `session.agent-profile`, on entities that are not in the spec's twelve, read the row through `tx` and report their own code as a content issue instead; `dependency.exists` reads its two Tasks the same way, which matches the spec, where it is a content `rule_violation` (`PROTOCOL.md:276`), and only the Elixir engine answers NotFound (`tasks/dependency/rules.ex:10`) (no gap code): M8.
- All entities: `expected-version` is one issue of an `InvalidInputError`, in declaration order beside any other failed check, where the spec files it under `version_conflict` (-32002) and checks it first (PROTOCOL.md:111, :210); the port's error mapping picks it out by code (G02): application code.
- Claim, Membership, Dependency: an update or destroy addresses the record by its own `id`, where the spec addresses it otherwise: `RenewClaimInput`, `ReleaseClaimInput` and `RevokeClaimInput` take the claim's `id` where the spec takes `taskId` (`schemas/protocol.ts:579-595`), `RevokeMembershipInput` the membership's `id` where the spec takes `collaboratorId` (`:467-471`), and `RemoveDependencyInput` the dependency's `id` where the spec takes `dependentId` and `prerequisiteId` (`:565-569`); a transport finds the record from the spec's params (no gap code): application code.
- Task, Claim, Run, Attempt: the state machines and their named transitions; `state` is an enum and each action would carry a check (G03): after 1.0.
- Task: the filtered has-ones (`currentAssignment`, `activeClaim`, `pendingSubmission`) as relationships; the file has the booleans `assigned`, `claimed` and `inReview`, written as `.some` over the unfiltered has-many, and application code reads the row itself with `.find` over the loaded list (G07): after 1.0.
- Task: the `reviewer` computed field (`{ collaboratorId, rule }`) and `blocked_reasons` (a list of `{ kind, taskId, message }`), which are structured results and not attributes; `reviewerFor` and `blockReasonsOf` in `src/domain/work/work.helpers.ts` build them through `tx` (G10, G29): application code.
- Task: the `lastSettledAt` rollup over a filtered subset of events; `lastCompletedOrReopened` in `src/domain/work/work.helpers.ts` computes it for `claim.invalidated` (G07): after 1.0.
- Task: `reopenedAt` is a field the spec's Task does not have (`schemas/protocol.ts:188-211`). `claim.invalidated` (`PROTOCOL.md:326`) needs the Task's last completion or reopen, and a reopen leaves no row, so `reopen` sets it and no input carries it; the last completion is the latest `completedAt` of the Task's completions. Hyper reads the time of its `complete` and `reopen` events instead (`tasks/task/rules.ex:184-192`), which the event log of M6 (G12) could do here. A claim that ends in the same millisecond as the last completion or reopen counts as ending before it (Mesh stores milliseconds, G24), until M6's order of events (G12) settles a tie. Reads return the field beside the spec's (G06, G07): not scheduled.
- Task: the `next` read's post-query filtering and its null ordering (G27, G37): application code.
- Claim, Dependency, Review, SessionReference, Attempt: the composite and partial unique indexes and the identity on a relationship key (`(task, fence)`, the dependency edge, one review per submission, `(runtime, runtimeSessionId)`, `(run, step, number)`, the active-only partials) (G08): after 1.0.
- Claim: the lease length is the constant `LEASE_MS` (ten minutes) in `src/domain/work/work.helpers.ts`, where Hyper reads `lease_ms` from its configuration (`tasks/claim/changes/lease.ex:24-25`) (G34): application code.
- Attempt: `attempt.claimer` is a permission denial in Hyper (`runs/attempt/rules.ex:15-30`, `Role.deny`); the port reports it as a content issue of `start` (G21, G22): M8.
- Invocation: an exact `estimatedCost`; `decimal` is a number, so it round-trips as a double (G38): not scheduled.
- SessionReference: `record` as an upsert (G09): after 1.0.
- Event: the event written in the same transaction as every change, with a gap-free sequence (G12): M6.
- Event: the spec's `id` beside `seq`; Mesh fills one key, so `seq` is the key and the wire `id` and the nested `record` object are assembled by the application (G12): application code.
- Event: the `subtree` read, a walk over descendants (G36): application code.
- Workspace: `owner_ids` and `stats`, results that are not a record (G10, G26): application code.
- Workspace: `export` and `import` (G18): after 1.0.

## The 13 effects

The gap analysis counts 13 Hyper actions that write other records in their own transaction (G05). An effect inside the command's aggregate is a step of the entity file's action; an effect on another aggregate is a function in `src/domain/<module>/<module>.commands.ts`, named by Hyper's method in camelCase (`task.cancel` is `taskCancel`), so no function can take a name `#mesh` exports (those put the action first, `cancelTask`). The aggregates are Hyper's (`tasks.ex:2`, `memberships.ex:2`, `machines.ex:2`, `runs.ex:2`): the Task aggregate holds its assignments, dependencies, claims, submissions, reviews and completions; the Run aggregate its attempts. Hyper's paths are under `lib/hyper/` in the Elixir engine; the first one names the line that attaches the change.

| Hyper command | Effect | Aggregate it writes | Where it lives | Hyper file and line |
| --- | --- | --- | --- | --- |

| `task.cancel` | revokes the claims and withdraws the pending submission; cancels the Task's running runs | Task; Run | `work/task.mesh.mx`, `cancel`; `taskCancel` (`work/work.commands.ts`) for the runs | `tasks/task.ex:81`; `tasks/task/changes/settle_work.ex:17-31` |
| `task.assign` | revokes the previous assignee's claims, ends the current assignment `reassigned`, starts the new one | Task | `work/task.mesh.mx`, `assign` | `tasks/task.ex:136`; `tasks/task/changes/reassign.ex:15-47` |
| `task.unassign` | revokes the assignee's claims and ends the assignment `unassigned` | Task | `work/task.mesh.mx`, `unassign` | `tasks/task.ex:144`; `tasks/task/changes/reassign.ex:15-47` |
| `claim.acquire` | expires a lapsed claim first; assigns an unassigned Task to the holder | Task | `work/claim.mesh.mx`, `acquire` | `tasks/claim.ex:58-59`; `tasks/claim/changes/lease.ex:44-51`; `tasks/claim/changes/assign_on_claim.ex:11-20` |

| `review.accept` | settles the submission `accepted` and completes the Task as `review-accepted` | Task | `work/review.mesh.mx`, `accept` (it calls `completeTask` with `context.completion`); `reviewAccept` (`work/work.commands.ts`) adds the `warnings` | `tasks/review.ex:39`; `tasks/review/changes/review.ex:10-31` |

| `attempt.finish` | settles the run, unless the attempt failed with a retryable error | Run | `execution/attempt.mesh.mx`, `finish` | `runs/attempt.ex:87`; `runs/attempt/changes/settle_run.ex:11-27` |

Calling a generated action directly skips the effect on another aggregate: `cancelTask` leaves the Task's runs running, `revokeMembership` and `retireCollaborator` leave the claims (and `retireCollaborator` the membership), and `startAttempt` and `recordSessionReference` take a Machine id instead of a host name. Tests and seeds call the functions (`test/composition.test.ts` pins both behaviours); a transport would expose the functions in the generated actions' place. `review.accept` passes `context.completion` to the nested complete, as Hyper does (`tasks/review/changes/review.ex:25-31`); any caller can set that key, so Task `complete` reads the submission it names through `tx` and throws a `FrameworkError` unless it is an accepted submission of that Task that no completion names yet, and a forged call writes nothing, except through the internal actions of G20 (an actor who settles his own submission `accepted` with the exported `settleSubmission` can then name it), until M8 (`test/composition.test.ts`, acceptance test 1). "Release the actor's claim", which `task.complete` and `submission.submit` both do, is the pure helper `claimToRelease` in `src/domain/work/work.helpers.ts`, which takes the claims and the time, never the model.

Versions (PROTOCOL.md §4.5): every command that changes the Task aggregate bumps the Task's `version` by exactly one, whatever it writes inside the aggregate: a write to a claim, submission, review, completion, assignment or dependency calls Task `touch` once, and a command that also changes the Task itself bumps it in its own `set` and does not touch it again. A late result does not bump it. `test/composition.test.ts` walks 26 commands (`task.complete` with a live claim and a summary, and `review.accept`, among them) and checks each one adds one; `membershipRevoke` over claims on two Tasks bumps each Task once. Workspace, Collaborator, Membership, Machine, SessionReference, Run and Attempt bump their own `version` in each action that changes them, with the same `expected-version` check.

What M4 added: the spec's computed fields that are one expression over a has-many are written and evaluated in memory (`test/expressions.test.ts`): Task's `childrenSettled` (rule `task.children-settled`), `claimed`, `inReview`, `assigned` and `lapsedClaim` (the `.some(...)` forms the spec uses instead of the filtered has-ones), and Claim's `lapsed` (rule `claim.expired`). The rules that read them are `check`s, which M5 runs (G07).

What M7 added: `Task.parent` and `Task.children`, `Run.parentRun` and `Invocation.corrects` relate to their own type with no import; `Task.dependencies` (`via=:dependent`) and `Task.dependents` (`via=:prerequisite`) follow the two keys Dependency holds to Task, and `Collaborator.memberships` (`via=:collaborator`) the first of the three Membership holds to Collaborator; Task has `blocked` (a prerequisite that is not done), `maxFence` (an unfiltered `max` over the claims, as the Elixir engine's aggregate) and `derivedState` (the spec's rule, first match wins: stored `done` or `canceled`, then `in-review`, `claimed`, `blocked`, `ready`; `test/relationships.test.ts` checks all 180 combinations of stored state, submission, claim and prerequisites against the spec's text). A relationship or computed field loads by name through `loadTaskFields` and its siblings; the cost of `Claim :acquire`'s reads is measured in the same test file and in the M7 report.

What M5 added, in `test/rules.test.ts` (roadmap M5 acceptance test 9): a passing and a failing case for each of Hyper's 57 rules (gap analysis, Appendix A), named by Hyper's own rule name as the issue `code`, except the two that need a policy (`role`) or a provider (`task.not-blocked`), which the test lists with their reason and milestone; a last test checks that the two lists together are the 57 (55 ported, 2 not), and that every code an entity file reports, at any depth under `src/domain/`, has its cases. `claim.invalidated` is a check of Task `complete` that only an unfenced call can fail, and not the completion `review.accept` makes (`PROTOCOL.md:283` names `task.complete` alone, and `:332` lists what `review.accept` re-checks), so a reviewer who once held a claim on the Task can still accept; it reads the Task's claims, completions and `reopenedAt` (see the Task line above), and a revoked or expired claim counts from its end or its lease end, whichever came first, since the spec treats a claim as expired the moment its lease runs out (`PROTOCOL.md:312`). `machine.retired` is reported too, on `attempt.start` and `session.record`, as Hyper's `ReportMachine` does; it is not one of the 57. The rules that read other entities (`collaborator.name-unique`, `membership.last-owner`, `membership.none-active`, `assignment.assignee-role`, `task.no-cycle`, the `dependency.*` rules, `evidence.exists`) read them through `tx`; `submission.none-pending` cannot fail alone through the actions, since a pending submission puts the Task in review and leaves no live claim (Hyper's rule is defensive, `tasks/submission/rules.ex:9`), so its failing case shows it beside `claim.current-fence` through the actions and then alone, over a live claim the test inserts beside the pending submission. `evidence.exists` reports a non-null `evidence` that is not a list of ids (`schemas/protocol.ts:603`) as missing, on `submission.submit`, `task.complete` and the late result. The relationships Hyper sets from the actor (`creator`, `holder`, `submitter`, `reviewer`, `completedBy`, `grantedBy`, `revokedBy`, `startedBy`, `performer`, `firstReportedBy` and the rest), the timestamps the engine sets (`acquiredAt`, `expiresAt`, `grantedAt`, `startedAt`, `endedAt`, `revokedAt`), `fence` (the Task's highest plus one), `number`, `taskVersion`, `claimFence`, Review's `ruleApplied` and the lease end are `set` from `actor` and `now()`, so no caller can pass them. `test/composition.test.ts` holds acceptance tests 1, 2, 3 (with two concurrent `acquireClaim` calls on one Task: one claim, one `claim.task-ready` with the derived state), 6 and 10 (`warnings` and the late result).
