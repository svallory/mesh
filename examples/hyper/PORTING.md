# Porting Hyper to Mesh: what the entity files leave out

The entity files in `src/domain/` hold what Mesh builds today: attributes, keys, relationships, the actions with their checks and steps, and, since M5, every effect a command has inside its own aggregate (entity calls and `privileged` reads in a `run` step, `run [after=:write]`). The effects that reach another aggregate, the `warnings` and the late result are plain TypeScript functions in `src/domain/<module>/<module>.commands.ts`, each one application transaction (`transaction(fn)` from `#mesh`). They follow the Hyper specification (`svallory/hyper-engine-spec`, branch `feat/protocol-phases`, commit `ccc00f9`: `PROTOCOL.md` and `schemas/protocol.ts`) and nothing else, as [ADR-0072](../../apps/docs/docs/architecture/decisions/0072-mesh-1-0-is-the-port-gate.md) requires; the five execution entities (Run, Attempt, Invocation, Machine, SessionReference) are not in the spec's twelve and follow the drafts in `notes/hyper-port/entities/`. Every read is the auto read: a caller's `{ filter, sort, limit, offset }` serves Hyper's `get_*`, `list_*` and `list_events`, so those reads are not omissions.

Each line names the entity, the construct left out, its code in the [gap analysis](../../apps/docs/docs/architecture/research/hyper-port-gap-analysis.md) (`G` for a gap, `D` for a draft finding), and the milestone of [roadmap revision 5](../../apps/docs/docs/architecture/roadmap/roadmap.md) that delivers it. "No gap code" marks a limit the analysis does not list.

- All entities: one rule reused by name across actions and entities, so each check is repeated (G04): after 1.0.
- All entities: the wire form of a denial. `ForbiddenError.policies` names the policies that refused a call, each named after the spec's check id (the table under "Permissions" below), and carries no per-check details, where the spec answers `permission_denied` (-32001) in the `permission` phase with the check ids and attaches `{ role, required }` to `role` and `{ reviewerId }` to `review.reviewer` (`PROTOCOL.md:246-254`); a collaborator with no membership is refused a query too (`PROTOCOL.md:132`, conformance `02:42-50`), where a Mesh read with a failing read policy gives no rows (ADR-0022), so HA checks the membership before it runs a query and returns that error itself. The daemon does both (`contextFactory` in `src/rpc/context.ts` refuses a caller with no active membership before any method runs, and `src/rpc/errors.ts` maps each policy to its check id and attaches `{ role, required }` to `role`, and `explained` there attaches `{ reviewerId }` to `review.reviewer`, read once the call's transaction has rolled back) (G22): application code.
- All entities: the actor. `context.actor` is `{ id, role }` (`src/context.ts`): HA must read the caller's collaborator and the role of its active membership (or `null`) from the database at call entry, refuse an unknown or retired actor there, and put both on `actor`, never from the request's payload, as Hyper's router resolves the actor (`transport/router.ex:102-120`); only the read policies (`membersRead`) use `role`, and every write policy reads the role through `privileged` inside the transaction (decision POL-20, ADR-0074); `contextFactory` in `src/rpc/context.ts` does this (no gap code): application code.
- All entities: a read's `load` input (the roadmap has no milestone for it); the `load` step of an action works, and `loadTaskFields(tx, rows, names)` and its siblings load a relationship or computed field inside a transaction (no gap code): not scheduled.
- All entities: filtering or sorting a read by a rollup or computed field (`maxFence`, `derivedState`) fails with an error that names M10 (G07): M10.
- All entities: the plugin hook points and blocking-condition providers; Task's `task.not-blocked` rule asks the providers (`tasks/task/rules.ex:82-88`), so `test/rules.test.ts` lists it as not ported (G11, G31): M6.
- All entities: microsecond timestamps; Mesh stores milliseconds (G24): not scheduled.
- All entities: an id in a required relationship that names no row fails with a `FrameworkError` when the action loads the relationship (and is stored as given when nothing reads it, SQLite having no foreign keys), where the spec answers `not_found` in the permission phase (PROTOCOL.md §4.4, the `exists` check, `:110`). Since M8b `claim.acquire` answers it for an actor with a membership: policy `claimAssignee` reads the Task through `privileged` and throws `NotFoundError` for an id that names no row (`assigneeMayClaimOf` in `src/domain/work/work.helpers.ts`), and the error leaves the call unchanged. An actor with no membership passes `claimAssignee` and is refused by `isMember` and `ownerOrMember` whether the Task exists or not, since a target the actor cannot see must answer as a missing one (`PROTOCOL.md:110`, `02:42`). The other creates follow the same helper before HP, the port gate: a create's checks see `self` before the input is applied (ACT-27), so until then a rule that asks about the record a create names (`task.open` on a submission or a run, `attempt.run-running`, `submission.pending` on a review, and the like) reads it through `privileged` by the id in `input` and refuses an id that names no row with its own code, and the `FrameworkError` is left to a step that loads the relationship. Three content codes must be reconciled with `not_found` when they move: `attempt.session` and `session.agent-profile` (on entities that are not in the spec's twelve, which report their own code as a content issue), and `dependency.exists`, which is a content `rule_violation` in the spec (`PROTOCOL.md:276`) and NotFound only in the Elixir engine (`tasks/dependency/rules.ex:10`) (no gap code): application code.
- All entities: `expected-version` is one issue of an `InvalidInputError`, in declaration order beside any other failed check, where the spec files it under `version_conflict` (-32002) and checks it first (PROTOCOL.md:111, :210); the port's error mapping in `src/rpc/errors.ts` picks it out by code (G02): application code.
- Claim, Submission, Collaborator: the outcome of a denied write that reads the stored row. Under option A of [ADR-0046](../../apps/docs/docs/architecture/decisions/0046-denied-atomic-write-outcome.md), the working assumption of the open decision POL-05, a record-reading write check is folded into the statement and a denied row is answered as not found; the policies `claimHolder` (renew, release), `submissionSubmitter` and `collaboratorSelfOrOwner` would then answer `not_found`, where the spec answers `permission_denied` with `claim.holder` (`05:53`), `submission.submitter` (`06:69`) and `collaborator.self-or-owner` (`02:123`, `02:132`). M8a evaluates them in memory on the locked row and answers forbidden, so nothing changes now; when POL-05 is decided, Hyper needs its option B or D (no gap code): after 1.0.
- Claim, Membership, Dependency: an update or destroy addresses the record by its own `id`, where the spec addresses it otherwise: `RenewClaimInput`, `ReleaseClaimInput` and `RevokeClaimInput` take the claim's `id` where the spec takes `taskId` (`schemas/protocol.ts:579-595`), `RevokeMembershipInput` the membership's `id` where the spec takes `collaboratorId` (`:467-471`), and `RemoveDependencyInput` the dependency's `id` where the spec takes `dependentId` and `prerequisiteId` (`:565-569`); a transport finds the record from the spec's params; `src/rpc/resolve.ts` does it: `membershipOf` finds the membership by its collaborator, `claimOf` the actor's claim on the Task by its fence (`claim.renew`, `claim.release`), `activeClaimOf` the Task's active claim (`claim.revoke`, which names no fence) and `dependencyOf` the edge between the two Tasks; where there is no such record, each answers the permission failure the policies would give first and then the content check (`claim.active`, `dependency.exists`) (no gap code): application code.
- Task, Claim, Run, Attempt: the state machines and their named transitions; `state` is an enum and each action would carry a check (G03): after 1.0.
- Task: the filtered has-ones (`currentAssignment`, `activeClaim`, `pendingSubmission`) as relationships; the file has the booleans `assigned`, `claimed` and `inReview`, written as `.some` over the unfiltered has-many, and application code reads the row itself with `.find` over the loaded list (G07): after 1.0.
- Task: the `reviewer` computed field (`{ collaboratorId, rule }`) and `blocked_reasons` (a list of `{ kind, taskId, message }`), which are structured results and not attributes; `reviewerFor` and `blockReasonsOf` in `src/domain/work/work.helpers.ts` build them through `privileged` (G10, G29): application code.
- Task: the `lastSettledAt` rollup over a filtered subset of events; `lastCompletedOrReopened` in `src/domain/work/work.helpers.ts` computes it for `claim.invalidated` (G07): after 1.0.
- Task: `reopenedAt` is a field the spec's Task does not have (`schemas/protocol.ts:188-211`). `claim.invalidated` (`PROTOCOL.md:326`) needs the Task's last completion or reopen, and a reopen leaves no row, so `reopen` sets it and no input carries it; the last completion is the latest `completedAt` of the Task's completions. Hyper reads the time of its `complete` and `reopen` events instead (`tasks/task/rules.ex:184-192`), which the event log of M6 (G12) could do here. A claim that ends in the same millisecond as the last completion or reopen counts as ending before it (Mesh stores milliseconds, G24), until M6's order of events (G12) settles a tie. Reads return the field beside the spec's (G06, G07): not scheduled.
- Task: the `next` read's post-query filtering and its null ordering; `task.next` in `src/rpc/methods.ts` reads the open Tasks with their derived state, keeps the ready ones the actor may claim and sorts them by priority, no priority last, then by creation (G27, G37): application code.
- Task: a reason that names the record a check found. Hyper's `task.children-settled` names each open child (`PROTOCOL.md:341`, conformance `03:175`), but a check's `message=` is fixed text in Mesh today, and its `details` carry only the children's ids, as the spec's do; `explained` in `src/rpc/errors.ts` reads their titles through `privileged` once the call's transaction has rolled back and appends them to the reason. Whether a check may compute its message is an open decision (no gap code): application code.
- Claim, Dependency, Review, SessionReference, Attempt: the composite and partial unique indexes and the identity on a relationship key (`(task, fence)`, the dependency edge, one review per submission, `(runtime, runtimeSessionId)`, `(run, step, number)`, the active-only partials) (G08): after 1.0.
- Claim: the lease length is the constant `LEASE_MS` (ten minutes) in `src/domain/work/work.helpers.ts`, where Hyper reads `lease_ms` from its configuration (`tasks/claim/changes/lease.ex:24-25`), and until then the daemon refuses `--lease-ms` as a usage error (G34): application code.
- Invocation: an exact `estimatedCost`; `decimal` is a number, so it round-trips as a double (G38): not scheduled.
- SessionReference: `record` as an upsert (G09): after 1.0.
- Event: the event written in the same transaction as every change, with a gap-free sequence (G12): M6.
- Event: the spec's `id` beside `seq`; Mesh fills one key, so `seq` is the key and the wire `id` and the nested `record` object are assembled by the application (G12): application code.
- Event: the `subtree` read, a walk over descendants (G36): application code.
- Workspace: `owner_ids` and `stats`, results that are not a record (G10, G26): application code.
- Workspace: `export` and `import` (G18): after 1.0.

## The 13 effects

The gap analysis counts 13 Hyper actions that write other records in their own transaction (G05). An effect inside the command's aggregate is a step of the entity file's action; an effect on another aggregate is a function in `src/domain/<module>/<module>.commands.ts`, named by Hyper's method in camelCase (`task.cancel` is `taskCancel`), so no function can be taken for a generated action, which is a method of the entity's value (`Task.cancel`, from `#mesh/domain/work`). The aggregates are Hyper's (`tasks.ex:2`, `memberships.ex:2`, `machines.ex:2`, `runs.ex:2`): the Task aggregate holds its assignments, dependencies, claims, submissions, reviews and completions; the Run aggregate its attempts. Hyper's paths are under `lib/hyper/` in the Elixir engine; the first one names the line that attaches the change.

| Hyper command | Effect | Aggregate it writes | Where it lives | Hyper file and line |
| --- | --- | --- | --- | --- |
| `task.complete` | records the Completion, settles the actor's own pending submission `accepted` or records an accepted one from the summary, releases the live claim | Task | `work/task.mesh.mx`, `complete`; `taskComplete` (`work/work.commands.ts`) adds the late result and the `warnings` | `tasks/task.ex:107`; `tasks/task/changes/record_completion.ex:15-58` |
| `task.cancel` | revokes the claims and withdraws the pending submission; cancels the Task's running runs | Task; Run | `work/task.mesh.mx`, `cancel`; `taskCancel` (`work/work.commands.ts`) for the runs | `tasks/task.ex:81`; `tasks/task/changes/settle_work.ex:17-31` |
| `task.assign` | revokes the previous assignee's claims, ends the current assignment `reassigned`, starts the new one | Task | `work/task.mesh.mx`, `assign` | `tasks/task.ex:136`; `tasks/task/changes/reassign.ex:15-47` |

Calling a generated action directly skips the effect on another aggregate: `Task.cancel` leaves the Task's runs running, `Membership.revoke` and `Collaborator.retire` leave the claims (and `Collaborator.retire` the membership), and `Attempt.start` and `SessionReference.record` take a Machine id instead of a host name. Tests and seeds call the functions (`test/composition.test.ts` pins both behaviours); a transport would expose the functions in the generated actions' place. `review.accept` passes `context.completion` to the nested complete, as Hyper does (`tasks/review/changes/review.ex:25-31`). Any code holding a context can set that key, so policy `reviewCompletion` on Task `complete` refuses a call that sets it without `system` (an actor-only `forbid-if`, decided before the transaction), and Task `complete` still reads the submission it names through `privileged` and throws a `FrameworkError` unless it is an accepted submission of that Task that no completion names yet, which guards a `system` call that names the wrong one; `Submission.settle` and the other actions only the effects call are `internal`, so no caller can settle a submission to name it (`test/composition.test.ts`, acceptance test 1). "Release the actor's claim", which `task.complete` and `submission.submit` both do, is the pure helper `claimToRelease` in `src/domain/work/work.helpers.ts`, which takes the claims and the time, never the model.

Versions (PROTOCOL.md §4.5): every command that changes the Task aggregate bumps the Task's `version` by exactly one, whatever it writes inside the aggregate: a write to a claim, submission, review, completion, assignment or dependency calls Task `touch` once, and a command that also changes the Task itself bumps it in its own `set` and does not touch it again. A late result does not bump it. `test/composition.test.ts` walks 26 commands (`task.complete` with a live claim and a summary, and `review.accept`, among them) and checks each one adds one; `membershipRevoke` over claims on two Tasks bumps each Task once. Workspace, Collaborator, Membership, Machine, SessionReference, Run and Attempt bump their own `version` in each action that changes them, with the same `expected-version` check.

What M4 added: the spec's computed fields that are one expression over a has-many are written and evaluated in memory (`test/expressions.test.ts`): Task's `childrenSettled` (rule `task.children-settled`), `claimed`, `inReview`, `assigned` and `lapsedClaim` (the `.some(...)` forms the spec uses instead of the filtered has-ones), and Claim's `lapsed` (rule `claim.expired`). The rules that read them are `check`s, which M5 runs (G07).

What M7 added: `Task.parent` and `Task.children`, `Run.parentRun` and `Invocation.corrects` relate to their own type with no import; `Task.dependencies` (`inverse=:dependent`) and `Task.dependents` (`inverse=:prerequisite`) follow the two keys Dependency holds to Task, and `Collaborator.memberships` (no option: the default picks `collaborator`, the one of the three Membership holds to Collaborator that is named after the entity); Task has `blocked` (a prerequisite that is not done), `maxFence` (an unfiltered `max` over the claims, as the Elixir engine's aggregate) and `derivedState` (the spec's rule, first match wins: stored `done` or `canceled`, then `in-review`, `claimed`, `blocked`, `ready`; `test/relationships.test.ts` checks all 180 combinations of stored state, submission, claim and prerequisites against the spec's text). A relationship or computed field loads by name through `loadTaskFields` and its siblings; the cost of `Claim :acquire`'s reads is measured in the same test file and in the M7 report.

What M5 added, in `test/rules.test.ts` (roadmap M5 acceptance test 9): a passing and a failing case for each of Hyper's 57 rules (gap analysis, Appendix A), named by Hyper's own rule name as the issue `code`, except the one that needs a provider (`task.not-blocked`), which the test lists with its reason and milestone, and `role`, a permission check in Hyper, whose cases since M8b assert the policy that refuses the call; `attempt.claimer` is both a rule and the policy `attemptClaimer`, as in Hyper, so its failing case asserts the policy for a caller and the rule for a call made as `system`; `submission.task-version` is on a list of its own: Hyper's engine refuses a review when the Task changed after the submission (`tasks/review/rules.ex:10-25`), but the spec has no such rule, since a review binds to the submission it saw and editing the Task afterwards changes nothing about it (conformance `06:128`), and the port follows the spec's v0 and nothing else (ADR-0072), so the rule is not ported; a last test checks that the four lists together are the 57 (54 rules, 1 policy, 1 not ported until M6, 1 not in the spec), and that every code an entity file reports, at any depth under `src/domain/`, has its cases. `claim.invalidated` is a check of Task `complete` that only an unfenced call can fail, and not the completion `review.accept` makes (`PROTOCOL.md:283` names `task.complete` alone, and `:332` lists what `review.accept` re-checks), so a reviewer who once held a claim on the Task can still accept; it reads the Task's claims, completions and `reopenedAt` (see the Task line above), and a revoked or expired claim counts from its end or its lease end, whichever came first, since the spec treats a claim as expired the moment its lease runs out (`PROTOCOL.md:312`). `machine.retired` is reported too, on `attempt.start` and `session.record`, as Hyper's `ReportMachine` does; it is not one of the 57. The rules that read other entities (`collaborator.name-unique`, `membership.last-owner`, `membership.none-active`, `assignment.assignee-role`, `task.no-cycle`, the `dependency.*` rules, `evidence.exists`) read them through `privileged`; `submission.none-pending` cannot fail alone through the actions, since a pending submission puts the Task in review and leaves no live claim (Hyper's rule is defensive, `tasks/submission/rules.ex:9`), so its failing case shows it beside `claim.current-fence` through the actions and then alone, over a live claim the test inserts beside the pending submission. `evidence.exists` reports a non-null `evidence` that is not a list of ids (`schemas/protocol.ts:603`) as missing, on `submission.submit`, `task.complete` and the late result. The relationships Hyper sets from the actor (`creator`, `holder`, `submitter`, `reviewer`, `completedBy`, `grantedBy`, `revokedBy`, `startedBy`, `performer`, `firstReportedBy` and the rest), the timestamps the engine sets (`acquiredAt`, `expiresAt`, `grantedAt`, `startedAt`, `endedAt`, `revokedAt`), `fence` (the Task's highest plus one), `number`, `taskVersion`, `claimFence`, Review's `ruleApplied` and the lease end are `set` from `actor` and `now()`, so no caller can pass them. `test/composition.test.ts` holds acceptance tests 1, 2, 3 (with two concurrent `Claim.acquire` calls on one Task: one claim, one `claim.task-ready` with the derived state), 6 and 10 (`warnings` and the late result).

## Permissions

Since M8b each entity file carries Hyper's permissions as policies, in place of the open stand-in M8a left. The spec decides where it and the Elixir engine differ (decision POL-20, [ADR-0072](../../apps/docs/docs/architecture/decisions/0072-mesh-1-0-is-the-port-gate.md)); the five execution entities follow the Elixir engine. Elixir paths are under `lib/hyper/`; `test/permissions.test.ts` holds the roadmap's M8 acceptance tests (1) to (8) on Hyper, the 19 cases of the spec's group 02 (all but `02:36`, `task.next`, which the port has no query for) the permission cases of the other groups, and three tables over a workspace with a row of every entity (every read by a non-member, a guest and `system`; every internal action called without `system`; every write `isMember` covers, with the full list of policies that refuse a non-member), and `test/rules.test.ts` the Hyper rule that is a permission check (`role`).

How the policies are written:

1. **The role gate is two policies.** `isMember` (the spec's `membership`: an active membership) and `ownerOrMember` or `ownerOnly` (the spec's `role`) read the actor's membership through `privileged` (`memberOf` and `roleIn` in `src/domain/identity/identity.helpers.ts`), so a membership revoked earlier in the same transaction is seen (ADR-0074). A collaborator with no membership fails both; the spec accepts the extra failure (`PROTOCOL.md:114`).
2. **Reads.** Every entity's `membersRead` admits an actor whose `role` is set, or `system`; a non-member's read gives no rows (see the first omission above for HA's part).
3. **The relationship checks** are separate policies, so `ForbiddenError.policies` names the spec's check id; each reads what it needs through `privileged` or `self` (the helpers in `src/domain/work/work.helpers.ts` and `src/domain/execution/execution.helpers.ts`).
4. **Internal actions.** The actions only an effect, the engine or HA calls are covered by `internal`, which admits only `isSystem(context)`. Hyper authorizes only the command the actor sent and runs every nested call with `authorize?: false` (`pipeline/changes.ex:26-31`); the port passes `{ ...context, system: true }` (or `nested(context)` from `src/context.ts`) on every nested call, keeping the human `actor`, and every policy admits `system`. The bootstrap grants the first owner as the engine, recorded as granted by that owner (`PROTOCOL.md:48`).
5. **Names.** A policy is named after the spec's check id in camelCase, which HA maps back; `role` is not a name, since Membership has an attribute `role`.

| Policy | Spec check id | What it admits |
| --- | --- | --- |
| `membersRead` | `membership` (HA answers a query) | reads: an actor with a role, or `system` |
