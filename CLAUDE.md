# CLAUDE.md

**Mesh** is a Bun-only TypeScript framework. The compiler parses `.mesh.mx` entity file syntax v4 through closed MX contracts into a plain-data entity model. `:name` declares, `&name` refers, and an imported `Name` names another entity. MX lowers `&name` in every position through Mesh's dialect (`packages/compiler/src/front-end/dialect.ts`). The production compiler never rewrites source or executes expressions.

Seven core generators, each a pure typed view rendered through a Jig template that a project can override from `.mesh-generators/`: `types`, `validators` and `actions` write three files per entity, `expressions` writes `<entity>.expressions.ts` for an entity that has an expression (every expression as one function of a scope: a translated tree printed as a call chain over `@meshfw/runtime`'s `expr`, a plain one as the authored TypeScript; the actions call them through `$expressions[id]($s)`), `load` writes `<output>/load.ts` when some entity has a relationship or a computed field (the load plan, plain data that `loadRows` in `@meshfw/runtime` follows, and one typed function per entity, `loadTaskFields(tx, rows, names)`, re-exported by the index; the record type has no relationship or computed member, `<Entity>Loadable` maps what load can attach and `<Entity>With<N>` is the loaded record; M5's `load` step calls these), `composition` writes `<output>/composition.ts` (the `Actions` and `Reads` interfaces, the types of `actions` and `tx`; it imports only the types files, so no actions file imports another), and `index` writes `<output>/index.ts` (`bind`, `connect`, `disconnect`, `transaction`, one delegate per action, type and `tables` re-exports); a plain emitter writes `model.json`, and the data adapter's generator writes `schema.ts`. A generated action runs the lifecycle written out phase by phase (M5, [ADR-0053](./apps/docs/docs/architecture/decisions/0053-validate-then-do.md)): enter and cast (`castInput`; a cast failure is reported alone, and inside a running transaction it fails that transaction through `failJoined`), plan (a create is one insert; every update reads the row first with `selectByKeyForUpdate`, a destroy only when a check or step can see it), the empty pre-check slot (policies are M8), one transaction holding the `validate` checks (`runCheck` collects every failed check into one `InvalidInputError`; an unknown result fails, ADR-0012 D1; `before` is the stored row, `self` the row with the input applied), the `do` steps (`set`, `when`, `load`, `run`), the data layer write (on an update that runs a function before it, `checkUnchanged` refuses the write when a call made in that phase changed the row; every generated write is counted with `noteWrite`), the `run [after=:write]` steps (inside the transaction, `self` the stored record, or the deleted row on a destroy; a `when` around one is evaluated before the write; the action then returns the row read again by key) and the loaded result. Composition (M5, [ADR-0068](./apps/docs/docs/architecture/decisions/0068-actions-compose-through-actions-and-tx.md)): a function of an entity file gets `actions` (every action function) and `tx` (every read body, without the read authorizer) from the composer (`compose.ts` in `@meshfw/runtime`) that the index's `bind` makes and hands to each `bind<Entity>(layer, options, composer)`, then fills with `provide` once every entity is bound; an entity bound alone gets stand-ins that throw `FrameworkError` when read. A nested call joins through the data layer's re-entrant `transaction` (calls joined to one transaction run one at a time, in the order they were made, each queued on its caller's frame; the base conformance suite checks it), carries the caller's context unless it passes its own, and a failed joined call makes the outermost call reject with a `FrameworkError` whose `cause` is the failure, even when caught; `#mesh` exports `transaction(fn, context)` with the same rule. What `actions`/`tx` return in an entity file is read-only like `self`; `input`, `before` and related records are `DeepReadonly` in the generated scope types (`<Entity>Loaded` is `self`), and `structuredClone` there is `cloneValue`, which returns a plain mutable copy. A computed field that reads `actions` or `tx` is `MESH_COMPUTED_COMPOSES`. The member passthrough (an omitted input keeps the stored value) applies to the member input `&x` only, never to an argument; `always` blocks run before the action's own, `bind(layer, { clock })` takes the clock `now()` reads, `mesh explain <entity> <action>` prints the plan (`typescript/explain.ts`); `policies` and `on:load` are listed in a comment as not run; a read takes the caller's `{ filter, sort, limit, offset }` (per-entity `<Entity>Filter`/`<Entity>Sort` types; `json` attributes are not filterable), a read that declares its own `filter`/`sort` in the file throws `FrameworkError` naming M10, as does a caller's `filter`/`sort` naming a computed field or rollup (the types and validators accept the names for that reason), and a create leaves the primary key to the data layer (UUIDv7, or the next integer under `integer-key-fill`). [Entities](./apps/docs/docs/docs/entities.md) is the language reference; [the decision records](./apps/docs/docs/architecture/decisions/0049-vocabulary-is-meshs-own.md), starting at ADR-0049, explain the design.

## Layout

Bun workspace (`workspaces`: `packages/*`, `apps/*`, `examples/*`), one root `bun.lock`.
- `packages/compiler` (`@meshfw/compiler`), three folders under `src/` ([ADR-0076](./apps/docs/docs/architecture/decisions/0076-compiler-front-end-and-back-end-are-separate.md); `test/architecture.test.ts` scans the imports): `front-end/` (MX IR to the model, language-neutral; the only code that imports `@mxlang/*`; `expression.ts` turns a function's Babel node into the expression tree or marks it plain, and reports free variables): closed v4 MX contracts (`contracts.ts`), Mesh's dialect (`dialect.ts`, the frozen `MESH_DIALECT`), the entity file extension list (`extensions.ts`, `MESH_EXTENSIONS`; nothing else spells `.mesh.mx`), the IR reader (`tree.ts`), the entity builder (`build.ts`; an entity names its own type with no import) and `relationships.ts` (after all entities are built: a `belongs-to` gets `keyType`, the type of its target's key, a `has-many`/`has-one` gets `via`, the `belongs-to` of the target it follows, from `via=:name` or the only candidate; several candidates, or a `via` that names no `belongs-to` back, is an error; no `belongs-to` back is not, it fails when loaded); `model/`: `BuildResult`, `ProjectDescription`, how a diagnostic is made, `checkExpressions` (types every tree across the model, warns, demotes to plain; the model itself is `@meshfw/model`) and `computeNeeds` (`Computed.needs`: the relationship and computed paths a body reads, so loading it loads them first; a plain body gives only the `&names` it reads; computed fields that read each other are an error; a plain body's `&name?.a?.b` chain is followed). `front-end/rollups.ts` also makes what is known to fail at load a build error: `sum`/`avg`/`min`, a rollup over a join (M10), a relationship with no `belongs-to` back that a rollup or computed field reads; `typescript/` (the back end; reads the model only, never imports `front-end/` or `@mxlang`): the generators (views in `typescript/views/`, plain data whose types are exported from the index and are the contract a project template renders; Jig templates in `typescript/templates/`, which only print view fields with `@if`/`@else`/`@each`/`{{ }}` (a trailing `~` on a tag trims its newline); `typescript/emitters/types.ts`, `validators.ts`, `load.ts`, `actions.ts`, `index.ts`; `renderGenerator` in `typescript/emit.ts`); `config.ts`, `paths.ts` and `index.ts` are the shell that calls both halves and the `model.json` emitter (tests in `test/`). Generated code imports only `@meshfw/runtime`, `zod`, its sibling files, the adapter's `schema.ts` and, in `index.ts` only, the project's `mesh.config.ts` (`connect()` imports it dynamically) (`checkGeneratedImports` in `test/repository-checks.ts`); the actions file reaches a table as `tables.<camelCase entity>`, the data-sqlite key rule. `parseEntitySource` in `front-end/build.ts` is the one `lowerSource` call: contracts, `dialect: MESH_DIALECT` (which carries `tagRules: "none"`; the compiler passes no `tagRules`), `structural`/`unknownTags: "reject"`, `imports: "pass"`; the test helper and the docs checks use it too (two unit tests, `test/syntax.test.ts` and `test/tree.test.ts`, call `lowerSource` with only `MESH_DIALECT` on purpose, to pin the lowered shapes without contracts)
- `packages/model` (`@meshfw/model`): plain-data entity model, eleven attribute types and four action types, diagnostic types, the expression tree (`ExprNode`) and the function registry (`FUNCTIONS`); imports nothing
- `packages/runtime` (`@meshfw/runtime`): the in-memory expression functions (`expr`, `scope`, `Clock`; ADR-0012 option A: unknown is `null`, tables in `@meshfw/runtime/testing` `EXPRESSION_TABLES`), flat, project-augmented `ActionContext` and `ContextArgument` (the generated action's `...[context]` rest tuple, optional until a required key is merged), errors, Standard Schema input validation, `loadRows` (M7: relationships by a second query for all the rows in chunks of 500 keys, a computed body after what it reads, `count`/`max` rollups through the data layer once per row, or from the rows when the same call loaded the has-many; a plain computed body gets a guarded record that throws on a relationship or computed field that was not loaded; a plain load plan, no knowledge of a database) and `rejectComputedQuery`, `DataAdapter` descriptors (with `build`, the adapter's build-half specifier), `defineConfig`/`MeshConfig` (here so a config imported at run time loads no compiler code) and data-layer contract v1; zero run-time dependencies; adapter conformance checks at `@meshfw/runtime/testing`
- `packages/data-drizzle` (`@meshfw/data-drizzle`, private): `drizzleOperations(commands, guard)`, contract v1 over a Drizzle table, shared by SQL adapters; depends on `@meshfw/runtime` and `drizzle-orm` only
- `packages/data-sqlite` (`@meshfw/data-sqlite`, private), two entries. Main (`src/index.ts`, run time; imports no model, compiler or drizzle-kit): `sqlite({ file })` returns one frozen value that is the `DataAdapter` descriptor and a lazily opened `DataLayer` (Mesh's own queued `BEGIN IMMEDIATE` transactions, `src/layer.ts`; `close()` returns it to unopened, so the next transaction reopens the same file and `disconnect()`/`connect()` reuse the configured layer), and `createSchema(db, tables)`. `./build` (`src/front-end/build.ts`, build time): the `AdapterBuild` whose `sqlite-schema` generator (`schemaView` + `templates/schema.ts.jig`) writes `.mesh/schema.ts`, and whose `db push` command backs `mesh db push`. `src/push-schema.ts` (`planSchemaPush`) is the one place that imports `drizzle-kit/api`, dynamically; `src/identifiers.ts` refuses backticks and control characters in names before any DDL
- `packages/cli` (`meshfw`): the Bun-only `mesh` developer command, a thin compiler shell; re-exports `defineConfig` from `@meshfw/runtime` (not the compiler) for compatibility, but a project's `mesh.config.ts` imports it from `@meshfw/runtime` (ruled in the PR #54 review: `connect()` loads the config at run time and `meshfw` is a dev dependency); runs the data adapter's commands (`mesh db push`) after the guard, with no adapter-specific code
- `packages/create-mesh` (`create-mesh`, public): the starter behind `bun create mesh`; today a placeholder bin that prints "Mesh is coming soon" and the site URL, published by the operator to reserve the name
- `apps/docs`: the docs site (docmd)
- `examples/hyper` (`hyper-example`, private): Hyper's 18 entities in four modules, with `Task.parent`/`children`/`dependencies`/`dependents`, `Run.parentRun`, `Invocation.corrects`, `Collaborator.memberships`, `maxFence` and `derivedState` (M7); `PORTING.md` lists what is left out and the milestone for each.
- `examples/blog` (`blog-example`, private): entity files under `src/domain/blog/`, committed output under `.mesh/` (including the adapter's `schema.ts` and `index.ts`, which `#mesh` maps to); `src/context.ts` declares a required `actor`; `bun run db:push` then `bun run start` runs `src/main.ts` against the gitignored `blog.db`; `bun run test` is `mesh build --check && bun test` (`test/blog.test.ts` binds `:memory:`; its connect tests run in a temporary working directory so `blog.db` is untouched)
- `tsconfig.base.json`: shared strict config that packages extend (root `tsconfig.json` covers `scripts/`); `scripts/verify.ts`: the `verify` runner

## Commands

- MX is a separate project, published on `https://npm.saulo.tech`; the root `bunfig.toml` scopes `@mxlang` to that registry and `packages/compiler` depends on `@mxlang/core` by exact version (currently `0.1.0-alpha.16`; `@mxlang/data` no longer exists and `package.json#mx` holds only `contracts`, never `target`; `@mxlang/tree-sitter-mx` stays at `0.1.0-alpha.2`). Alpha.16's `lowerSource` returns `{ ir, diagnostics }` (IR version 2, `ir` undefined on any error, never throws). A tag is a `DelegatedTag` node; an attribute is `static` (string, atom or member, told apart by `atom` and `member`), `boolean`, `dynamic`, `bound` or `spread`; a tagless member line is a `member` tag with `trigger.id === "member"`. Imports are `ir.imports` (`from`, `names`, name `span`/`localSpan`). `src/front-end/dialect.ts` builds `MESH_DIALECT` from Mesh's own syntax rows in `src/front-end/syntax/` (`atoms-sugars.ts`, `member.ts`, `mesh.ts`, ported from MX's reference module at MX commit `750c80ec1`; MX deletes its copies after Mesh sends DONE; Mesh owns all of its syntax): id `mesh`, name `Mesh`, `tagRules: "none"`, no `#id`/`.class` rows. The syntax files import only the public `@mxlang/core` API, and `test/no-core-syntax-import.test.ts` fails on any import of `@mxlang/core/syntax` in `packages/` or `examples/`. The value row `atom-value` and the `Atom` node type name the dialect, so the id must stay `mesh`; a whole-value atom (`via=:owner`) lowers to the same atom-marked `static` attribute as an atom elsewhere (`Attr.node` stays unset). The atom contract checks are Mesh's (`atomsHooks.afterLower` in `syntax/atoms-sugars.ts`) and see value atoms (`test/atom-values.test.ts`); an unspaced name (`uuid:id`, `<string:title/>`) is refused there as `MESH_UNSPACED_NAME`, since Mesh does not port core's tag-head sugar. Members are read from those shapes only, never from `Expr.code` (printed `self.x`); authored text is the source sliced at `Expr.span`. `meshfw`'s package.json declares `mx.dialect` (`id: "mesh"`, `extensions` equal to `MESH_EXTENSIONS`, `module: "./dist/dialect.js"`); `bun run build` in `packages/cli` (`scripts/build-dialect.ts`, part of `verify`) bundles `src/dialect.ts` into that plain-JavaScript file, fails when the manifest drifts from `MESH_EXTENSIONS`, and `packages/cli/dist/` is gitignored. `prepare` runs the same build, so `bun install` and `bun pm pack` produce `dist/`. MX loads the module in whatever runtime hosts it (Bun in Mesh's tests) and the file must be JavaScript Node can also load, so the module can never be `.ts`; `@meshfw/compiler` exports `./extensions` (the extension list) for the build script, so installing does not load the whole compiler. `mx.contracts` stays on `@meshfw/compiler`; MX rejects any other unknown top-level `mx` key. `bun install` at the repo root is all there is: no `bun link`, no token, no local MX checkout. `bun run verify` runs on GitHub Actions (`.github/workflows/verify.yml`) on every pull request and every push to `main`. To work against an unreleased MX commit, run `bun link` inside the MX checkout and temporarily point `packages/compiler`'s two `@mxlang` dependencies at `link:` (or at a `file:` path), then revert before committing; never commit a `link:` entry, and never run `bun link @mxlang/...` at the root, which writes a `link:` dependency into the root `package.json`.
- Jig: `@jig-lang/jig` is pinned exact (`1.0.1`, from npm) as a dependency of `@meshfw/compiler` only; `src/typescript/render.ts` is its one import site (a test enforces it; runtime, model, the CLI and generated code never import it). Jig's disk loader resolves `.edge` only, so Mesh reads each `*.ts.jig` file itself and renders with `await edge.renderRaw(contents, view, templatePath)` (`templatePath` is only what errors name; do not use `renderRawSync`, whose wrapper has the wrong signature). `{{ }}` does not escape, and the final newline is dropped (Prettier restores it). A Jig error is `MESH_TEMPLATE_RENDER` at the template's line and column.
- The MX packages are consumed from their published `dist` directories. `Cannot find module '@mxlang/data'` after a successful install means the installed version is broken or the scope entry was lost; check `bun.lock` for the `@mxlang` entries. Never build inside the MX checkout yourself.
- `bun run verify` runs every workspace package's `test`, `typecheck`, `build` and `validate` scripts (plus a type check for `scripts/`), including the docs build/link check, the blog generated-tree guard and generated-file type check, and compiler tests for the MX import boundary and complete MX fenced samples in `apps/docs/docs/docs/*.md` plus ADR-0050's reference. The Docs pages write **syntax v4** (`entity :Todo`, `belongs-to :list entity=List`, `input` with `&title`, `set` with `&done=true`). Docs checks report entity files checked and findings. Docs fences parse as authored through `parseEntitySource`; no normalisation or relaxed contracts. Before parsing, `checkDocsSyntaxV4` and `oldSpellingInV4` reject obsolete spellings, undeclared member heads, unimported entity identifiers and `self.` without destructured self parameters in that function; misplaced member lines and input assignments are parse errors. This is a bounded text guard, not full contract/type checking; planted tests pin those failures. `apps/docs/plugins/mx-highlight.js` carries one counted allowance, `MX_V4_INPUT_PENDING_SYNTAX_TABLE`: alpha.2 treats `input` as an HTML void tag, so nested input sections and bare member lines get same-width stand-ins for highlighting only. Rendering always uses authored text. MX owns the permanent fix (`mesh-syntax-highlighting-route`); both highlighter allowances stay until `@mxlang/tree-sitter-mx` moves past alpha.2, even though the parser pin no longer needs bridging. Other grammar errors still fail the build. Verification exits non-zero and names the failed step. The full Todo copies (Introduction, Tutorial and Entities) are byte-identical after stripping figure annotations; the home is a deliberate shorter excerpt whose shared lines must match. Quick start now runs the starter's single List entity and contains no MX fence. `apps/docs` also type-checks every TypeScript sample on the Docs pages against `apps/docs/samples/mesh-api.d.ts`, the declarations of the proposed API; a fence titled `(excerpt)` is skipped. `bun run test` and `bun run typecheck` run one kind only. Run `verify` before a PR.
- With `meshfw` installed, run `mesh build`, `mesh build --check`, `mesh inspect [entity]`, `mesh export generators`, `mesh db push [--force]` or `mesh --help` from the project root containing `mesh.config.ts` (no upward search). Templates are looked up once per build: `<project>/.mesh-generators/<template>` when it is a regular file, else Mesh's `packages/compiler/src/typescript/templates/<template>`; symlinks and non-regular entries there are `MESH_TEMPLATE_READ`. `mesh export generators` writes Mesh's templates into `.mesh-generators/` and writes nothing (exit 1) when an existing one differs; `examples/blog/.mesh-generators/` is never committed. After changing an entity file, a view or a template, rebuild the committed example with `cd examples/blog && bunx mesh build` and commit `.mesh/` with the source change. The blog's workspace dependency on `meshfw` supplies the local `mesh` command; for another project in this checkout, invoke it with `bun /absolute/path/to/packages/cli/src/bin.ts` from that project. Build never deletes files; move or delete stray output files yourself. The guard writes nothing and compares bytes, rejecting symlinks. Exit codes: 0 success, 1 build/config/guard errors, 2 usage errors.
- Data layer: `drizzle-orm` is pinned exact at `0.45.3` (a dependency of `data-drizzle`, `data-sqlite` and the user project) and `drizzle-kit` at `0.31.11` (a dev dependency and optional peer of `data-sqlite`, and a dev dependency of the user project); an upgrade is its own PR. Drizzle is mentioned only under `packages/data-*`, in a project's `.mesh/schema.ts`, in manifests and lockfiles (`checkDrizzleImports` in `packages/compiler/test/repository-checks.ts`). `DataAdapter.build` names the adapter's build half; `loadAdapterBuild` in `packages/compiler/src/typescript/adapter.ts` resolves it from the project root and requires a default `AdapterBuild { generators, commands? }` (`MESH_ADAPTER_BUILD`). Adapter generators set `Generator.templateDir` (absolute); their template names must not repeat a core one. `mesh db push [--force]` runs the guard first (a stale tree is refused), then the adapter's command: `:memory:` is refused, data-loss statements need `--force`. drizzle-kit draws a spinner on stdout during a push; `planSchemaPush` mutes it. Adding drizzle-kit nests docmd's esbuild in the root lock; `apps/docs/shared-lock-check.js` compares versions as sets for that reason.
- `defineConfig` requires `domain`, `output` and `data`; extensions are optional objects with a `name` string. A folder's path is the domain root; a glob uses its static directory prefix, and a file list its common parent. Entity modules are relative parent paths (`sales/billing`, or empty at the domain root); module segments permit letters, digits, `-` and `_`. Adapter options never enter `model.json`; only the adapter name does. The compiler's runtime-reference test emits real `.d.ts` and checks the documented runtime members against them without changing `apps/docs/samples/mesh-api.d.ts`.
- Docs site, from `apps/docs`: `bun run dev` (preview), `bun run build` (static site into `apps/docs/site/`), `bun run validate` (link check). How to add pages: `apps/docs/docs/architecture/contributing.md`.

## Rules

- The user-facing CLI package is `meshfw` (binary `mesh`; it re-exports `defineConfig`, but projects import `defineConfig` from `@meshfw/runtime`); the starter is `create-mesh` (`bun create mesh todo-app`). Other framework packages remain `@meshfw/*`. These are the workspace package names and the documented 1.0 naming. User docs write `mesh build` and other `mesh` commands; Quick start alone explains the `bunx mesh build` local-binary alternative.
- User docs separate `configuration.md` (project/context/adapters/environment) from `command-line.md` (commands/flags/exit codes). `using-your-domain.md` replaces the old Calling actions page. Framework integration snippets are explicitly `(excerpt)` fences; the sample checker counts exclusions dynamically rather than claiming they compile.
- `plugins/mx-figure.js` also injects site title/heading CSS and strips paired code backticks from docmd's known plain-text title labels at build time. It must not rewrite authored code blocks, URLs or escaping. `apps/docs/test/browser/docs-structure.mjs` checks the sidebar/home link, heading scale and title labels in both themes; it needs `SHOTS_DIR`, `SITE_DIR` and `PLAYWRIGHT_MODULE` (Playwright Docker), separately from `verify`.
- `typescript` and `@types/bun` are declared only in the root `package.json`; packages do not repeat them.
- Use bun, never npm.
- Always write "Mesh" (never "Mash").
- Architecture docs hold what cannot be understood from a single code file.
- The `@mxlang` scope resolves from `https://npm.saulo.tech`, the operator's read-only npm registry (no uplink);
  `bunfig.toml` points only that scope at it. `@mxlang/tree-sitter-mx` is what the docs site highlights `mx`
  with; a docs fix goes in `apps/docs/plugins/mx-highlight.js` (the docmd plugin, the capture-name palette)
  or goes to the MX lead as a grammar gap.
- `apps/docs/plugins/mx-highlight.js` is MX's highlighter's docmd plugin and not ours to fork: the grammar
  and the queries belong to MX. Change the palette only, except for the explicitly approved, tested,
  counted v4 input allowance above and `MESH_V4_MEMBER_RENDER`: a Mesh-side render-only overlay
  that colours operand/bare/sort `&name` heads as `ts-member`, leaving literals, comments and infix
  operators alone. Both bridges go away with `mesh-syntax-highlighting-route` (MX decision 182
  addendum 1). Do not patch the grammar or broaden either bridge silently.
- Home token explanations live in `apps/docs/plugins/mesh-home-hints.js`, wired by `mesh-home.js`.
  Keep descriptions outside the code so copying and the home-sample hash retain the authored file;
  every token in the fixed excerpt is checked against the commissioned wording. Each note has a shared
  family sentence followed by optional context; inline fragments use `mxHighlighter` at build time
  (TypeScript through its injection grammar), never a browser highlighter. Reference tokens name
  scoped targets for a single dashed SVG connector and outline. Keyboard navigation has one tab stop
  per nonblank line, with Left/Right and Home/End within it. Mutation/resize observers run only while
  a note is open; the panel is re-created after body replacement. Browser interactions and screenshots
  are exercised by `apps/docs/test/browser/home-hints.mjs` in Playwright's Docker image, separately
  from `bun run verify` (see the script header for its environment variables; screenshots default
  under `os.tmpdir()`, not the checkout).
- docmd 0.9.7 reads a raw HTML block until its tags balance, blank lines included, so Markdown (a fence
  above all) inside an open `<div>` is emitted as raw text. Wrap fences in a docmd container (`::: grids`)
  instead, and keep each HTML block self-contained. docmd also hides `<html>` until its theme script runs;
  `plugins/mx-figure.js` adds the `<noscript>` rule that keeps the site readable without JavaScript.
