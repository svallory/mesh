The local bus (M6 PR 4; spec `notes/spec/events-and-commands.md`, section "`localBus`, the first adapter"). `packages/bus-local` exports `localBus(options?)` and `LocalBusOptions { pollInterval?, retryDelays?, maxQueue? }` (a bad option is a `FrameworkError`; `pollInterval` and each delay are whole milliseconds no larger than 2147483647, the longest `setTimeout` keeps); its manifest is `{ adapter: "local", capabilities: ["ordered-delivery", "replay", "subscribe"] }`. `create` registers only `core.onClaimLost` and sets no timer. A round is sequential and never overlaps another (`wake()` coalesces with an `again` flag, and the loop clears `running` in a `finally` in the same turn as its last check, so a wake-up just after it starts a new round); it starts on `onPublished`, on the `pollInterval` timer (1000 ms) and when a backoff timer fires. Started delivery calls `core.runHandler` itself and keeps one lane per handler: a retryable failure waits on that handler's own timer (`retryDelays`, `[100, 1000, 10000]` by default) while the round skips it and goes on with the others; a non-retryable failure or the last retry stops the handler, reported once through `console.error` as a `HandlerStoppedError`, until `resumeHandler(name)` or the next start. `deliver()` uses `core.retry` with no wait (`[0, 0, 0]` unless `retryDelays` is set) and throws one `HandlerStoppedError` for the round. `MESH_DATABASE_BUSY` and `MESH_DELIVERER_LOST` are never counted as a try. A failure that ends after `stop()` or a lost claim schedules and reports nothing, and `stop()` clears the back-off timers again after the round it awaited. A handler whose cursor read fails (`MESH_EVENTS_DELETED`, `MESH_CURSOR_AHEAD`) stops alone, at the position after its cursor; the round goes on. A reporter that throws is caught. Subscriptions are fed with `{ maxQueue }` only when the option is set (else core's 10 000). Claim renewal stays core's. `resumeHandler(binding, name)` in `runtime/src/deliverer.ts` (exported by `#mesh` in event projects as `resumeHandler(name)`) calls the optional `EventBusInstance.resumeHandler?(handler)` and is a `FrameworkError` without a started delivery, for an unknown handler, or on a bus that lacks the hook. Commands, `on=` and `dispatch` (M6 PR 5; spec `notes/spec/events-and-commands.md`, sections "Answering a command" and "`dispatch`"). `create`, `update` and `destroy` take `on=` (an expression attribute: `answers` in `front-end/contracts.ts` accepts an identifier or one member of a namespace import with `isReference`, and refuses a wrapped value at its `valueSpan`, both as `MESH_UNKNOWN_COMMAND`; the name slot is optional on those three, and a bare `update` is `MESH_NAME`; `read` keeps its closed contract, so `on=` there is MX's `MESH_UNKNOWN_OPTION`; a string is MX's `MESH_OPTION_VALUE`, as for `entity=`). `buildEntity` resolves it with `resolveReference` and the `command` reference kind (`referenceKind("command", ...)`, code `MESH_UNKNOWN_COMMAND`, scope without `own`), names an unnamed action after the command's class (`Action.name`, first letter lower-cased, whatever the file binds) and records `Action.command` (`CommandRef { identifier, from, fqn, position }`; `fqn` is filled in `buildModel` once every command is built; absent without `on=`, so a project without commands keeps its model.json). A computed name that clashes is `MESH_DUPLICATE_MEMBER` with the command named (`authorNamed` tells it from a written one). `model/commands.ts` `checkCommands(document, diagnostics, complete)` runs last: `MESH_COMMAND_ANSWERED_TWICE` at the later `on=`, `MESH_COMMAND_INPUT` (the optionality rule `inputOptional` in `model/input-optional.ts`, shared with `entityInputs`: the key of an update or a destroy is required, a member input is optional off a create, a nullable or defaulted one is optional; an argument is a field like a member), and the warning `MESH_COMMAND_UNANSWERED`, which is skipped when a file did not parse (`complete` false). A test that declares a command only to name it in a `publish` filters that warning (`events.test.ts` shadows `buildModel`). `dispatch` is `dispatchCommand(table, command, context)` in `runtime/src/dispatch.ts` (reads the instance's `constructor[DECLARATION]` and calls the table entry with the instance; a non-command or a command missing from the table is a rejected `FrameworkError`) plus the generated block of `.mesh/index.ts` (`commandsView` in `typescript/views/index.ts`, the end of `index.ts.jig`): the answering entity values imported from their actions files, the command classes imported as types, one typed `run` per command that builds the action's input from the command's fields (no cast, so tsc on `.mesh/` finds a field of another type than the input's; the build checks names only), `DomainCommand` (the answered commands only, so an unanswered one is a type error), `DispatchResult<C>` (`ActionResult<typeof Entity.action>`, a runtime type: spelling `Awaited`/`ReturnType` needs new `GLOBAL_ALIASES`, which would change every project's `$globals.ts` and the corpus golden) and `dispatch`. It is an ordinary entity call, so it joins the transaction in the async frame; the handler context needs no `dispatch` (it is imported from `#mesh`). `mesh explain` prints an `answers` line. The CLI's `test/events.test.ts` runs it end to end through the fixture's `update on=PayInvoice`; `compiler/test/commands.test.ts` has every build code and the generated `index.ts` goldens (`fixtures/commands-golden`).

## Commands

- MX is a separate project, published on `https://npm.saulo.tech`; the root `bunfig.toml` scopes `@mxlang` to that registry and `packages/compiler` depends on `@mxlang/core` by exact version (currently `0.1.0-alpha.34`; `@mxlang/data` no longer exists and `@meshfw/compiler`'s `package.json` has no `mx` key; `@mxlang/tree-sitter-mx` stays at `0.1.0-alpha.2`). `lowerSource` returns `{ ir, diagnostics }` (IR version 7, `ir` undefined on any error, never throws). A tag is a `DelegatedTag` node; an attribute is `static` (string, atom or member: an atom carries `node: { type: "mesh:Atom", name, span }`, a member after a kind `node: { type: "mesh:Member", name, span }`), `boolean`, `dynamic`, `bound` or `spread`; a tagless member line is a `member` tag with `trigger.id === "member"`. Imports are `ir.imports` (`from`, `names`, name `span`/`localSpan`). `src/front-end/dialect.ts` builds `MESH_DIALECT` from Mesh's own syntax rows in `src/front-end/syntax/` (`atoms-sugars.ts`, `member.ts`, `mesh.ts`, ported from MX's reference module at MX commit `750c80ec1`; MX deletes its copies after Mesh sends DONE; Mesh owns all of its syntax; `transaction.ts`, the `%.name` row, is Mesh's own, modelled on the `&name` row as the MX lead advised, with no new MX alpha): id `mesh`, name `Mesh`, `tagRules: "none"`, no `#id`/`.class` rows, and the syntax table's `tagShorthands: false` (MX alpha.28, `syntax/mesh.ts`): a line head has no `#id`/`.class` shorthand, a `.` continues the tag name (`billing.InvoiceVoided` is one tag, which no section takes yet, so it is `MESH_UNKNOWN_TAG`), `#x`, `.x` or a `#` inside a head is `MESH_NO_TAG_SHORTHAND`, and `a.` or `a..b` is `MESH_INVALID_TAG_NAME`. The dialect also carries Mesh's vocabulary and its strictness (since MX alpha.21): `contracts: MESH_CONTRACTS` (`Dialect.contracts` is `@unstable` in MX), `structural: "reject"`, `unknownTags: "reject"`, `imports: "pass"`. Since MX alpha.29 it carries `messageVocabulary` (`@unstable`; `MESH_MESSAGE_VOCABULARY` in `front-end/dialect.ts`): MX's messages call a `key=value` an "option" (`attribute: { one: "option", many: "options", article: "an" }`) and a Mesh file a "Mesh file" (`file`), and `formatTag` spells a tag as its line is written (`&title`, `attributes`, `${x}`; never throws, `undefined` for a name it cannot spell). `tree` is unset (since alpha.30 no message reads it); the static-file messages read "Mesh files are static, so they do not evaluate `if`". Since alpha.31 a contract with an `analyze` hook (all of Mesh's) is worded the same way, and `formatTag` also receives MX's built-in names (`if`, `const`, ...), which Mesh spells as written like any other tag (no special case); built-in messages drop MX-syntax examples (`<const/name=value/>`). Under `structural: "reject"` a `for` or `if` under a contract tag is `MESH_STRUCTURAL_CONSTRUCT` at the construct, with no error for what it holds. Mesh's own hook messages say "option" where they mean a `key=value`. A caller of `lowerSource` passes the dialect and nothing else, never `customTags` (a passed `customTags` overrides the dialect's `contracts` silently) and no strictness option, so the editor checks a Mesh file exactly as the CLI does. Build `MESH_DIALECT` once and freeze it: MX re-validates an unfrozen dialect object on every call (about 46 ms instead of 3 ms). A test of the syntax alone uses `SYNTAX_DIALECT` (`test/syntax-dialect.ts`), the dialect without contracts or strictness. The syntax files import only the public `@mxlang/core` API, and `test/no-core-syntax-import.test.ts` fails on any import of `@mxlang/core/syntax` in `packages/` or `examples/`. Since MX alpha.33 core has no atoms: every `:name` is Mesh's `mesh:Atom` node type (`nodeTypes: { Atom }` in `syntax/mesh.ts`), named by the `atom` expression row and the `atom-value` row, so the id must stay `mesh`. Inside an expression core lists each atom in `Expr.nodes` with its forward (the `StringLiteral` its `lower` returns, the very object in `Expr.node`); Mesh finds an atom by forward identity (`atomForwards` in `front-end/tree.ts`); since alpha.34 core sets and reads no mark (`extra.mxAtom`, `extra.mxMember`), and Mesh sets none on its forwards. A whole-value atom (`inverse=:owner`) is a `static` attribute with `node`. Contracts type an atom option `mesh:Atom` and a list of atoms `{ type: "array", items: "mesh:Atom" }` (`values`, `types`, `auto`); a single atom in a list slot is refused (write `[:read]`). Since MX alpha.34 core has no members either: every `&name` is Mesh's `mesh:Member` node type (`nodeTypes: { Member }`, `syntax/member.ts`), named by the `member` expression row (`MEMBER_NODE`); in an expression its forward is `self.name` and Mesh finds it by forward identity (`memberForwards` in `front-end/tree.ts`, read by `readMember`, `readMembers`, `readMemberPath`, the expression translator and `contracts.ts`). After a kind (`sort asc &dueOn`) the `member` attribute row places a `static` `member` attribute with the node, asking `ctx.attribute` for `once`, so a second member is `MESH_SYNTAX` (`MX_INVALID_TRIGGER_USE`) at the second. Contracts type a single-member option `mesh:Member`; `checkMemberSlots` (Mesh's `afterLower`) refuses an expression there that is not exactly one member (`MESH_OPTION_VALUE`), which core's node-type check passes. Both node types declare `schema` (required since alpha.34) and a `label` (`atom`, `member`) that core's contract messages show (`must be atom, got string`). `extra.mxTransaction` (`%.now`, `%.today`) is Mesh's own mark and still reaches its readers: core passes a forward's `extra` through. `parseEntitySource` passes the entity file's absolute path, so core checks Mesh's marks against the project's other installed dialects as the editor does (`test/dialect-marks.test.ts`). The atom contract checks are Mesh's (`atomsHooks.afterLower` in `syntax/atoms-sugars.ts`) and see value atoms (`test/atom-values.test.ts`); since alpha.17 core has no name sugar or atom lexing (`:x` in a `.mx` file is plain JavaScript; a dialect row or node type builds it) and ships no dialect: a colon in a tag head is part of the tag name (`uuid:id`, `<string:title/>`, `entity:Todo`, `<:x/>` are unknown tags to MX), and an `afterLower` hook sees only the tags a contract names, so the dialect's `explainUnknownTag` hook (`front-end/dialect.ts`; `@unstable` in MX) refuses a name with a `:` as `MESH_UNSPACED_NAME`, replacing MX's own unknown-tag error for it (one lowering; the `:x` wording reads the parent contract's `defaultTag` from the hook's ancestors). Core no longer checks the atom contract keys: `values`, `pattern`, `ref` and `declares` are claimed by Mesh's `contractFields` and checked in its `checkContract`/`afterLower`. `run [after=:write] (...) {}` lowers to one `value`; a real duplicate warns with code `MESH_DUPLICATE_OPTION`. Match diagnostics by `code`, never by message text. MX's codes reach Mesh under Mesh's names (MX alpha.27): `MESH_DIALECT.diagnosticCodes` is `MX_TO_MESH_CODES` (`src/front-end/diagnostic-codes.ts`), `MX_X` as `MESH_X` (`MX_UNKNOWN_TAG` is `MESH_UNKNOWN_TAG`) with MX's "attribute" read as Mesh's "option" (a `key=value` on a line is an option, an attribute is an entity's data member: `MX_UNKNOWN_ATTRIBUTE` is `MESH_UNKNOWN_OPTION`, `MX_PARSE_INVALID_ATTR_TYPE_PARAMS` is `MESH_PARSE_INVALID_OPTION_TYPE_PARAMS`, an MX attribute tag is an option tag), except the commented entries, which reuse a Mesh code for the same mistake or take Mesh's word (`MX_INVALID_ATTRIBUTE_VALUE` is `MESH_OPTION_VALUE`, `MX_NOT_IN_DATA_FILE` is `MESH_NOT_IN_ENTITY_FILE`, `MX_DUPLICATE_DECLARATION` is `MESH_DUPLICATE_IMPORT`); MX renames the final diagnostics of `lowerSource` and of its project scan (`checkDialectFile`), so the build and the editor show one code, and Mesh, which runs no project scan, calls `diagnosticCodesOf` nowhere. `MX_KEPT_CODES` stay `MX_*` (`MX_INTERNAL_ERROR`, `MX_DIALECT_HOOK_ERROR`, `MX_DIALECT_ERROR`, `MX_DIALECT_WARNING`: a bug in MX or in a Mesh hook), as does the error of a dialect that fails to load. `test/diagnostic-codes.test.ts` fails when an MX alpha adds a code the map leaves out (the type of `MX_TO_MESH_CODES` fails the type check too): give it an entry by the same rule. Mesh's own codes come through `ctx.fail(message, { at, code: "MESH_X" })` (never a `MESH_X: ` message prefix) and are never renamed, and `buildModel` keeps every code it gets, so the build's diagnostics carry `MESH_UNKNOWN_TAG` as the editor shows it (`mesh build` prints each one: `file:line:column severity CODE message`, from `formatDiagnostic` in `@meshfw/model`); `meshDiagnostic` maps a diagnostic with no code to `MESH_SYNTAX` (a fallback no `.mesh.mx` source reaches). The CLI prints every line with its code; a diagnostic with no code prints without one. Under `unknownTags: "reject"` an unknown tag in a closed parent gives only `MESH_UNKNOWN_TAG`; the by-text pair filter is gone. An unnamed tag in a closed parent takes the nearest parent contract's `defaultTag`, so `<set><#a/></set>` gives one error. A spaced `#id`/`.class` is Marko's "Invalid attribute name"; `<x=1 :n=2/>` is Marko's "Expected a single expression, but found `:` after it." (`MESH_EXPECTED_SINGLE_EXPRESSION`). Members are read from those shapes only, never from `Expr.code` (the authored text with the triggers spliced in, `&title` lowered to its stand-in; only a method shorthand's `code` is printed); authored text is the source sliced at `Expr.span`. `meshfw`'s package.json declares `mx.dialect` (`id: "mesh"`, `extensions` equal to `MESH_EXTENSIONS`, `module: "./dist/dialect.js"`); `bun run build` in `packages/cli` (`scripts/build-dialect.ts`, part of `verify`) bundles `src/dialect.ts` into that plain-JavaScript file, fails when the manifest drifts from `MESH_EXTENSIONS`, and `packages/cli/dist/` is gitignored. `prepare` runs the same build, so `bun install` and `bun pm pack` produce `dist/`. MX loads the module in whatever runtime hosts it (Bun in Mesh's tests) and the file must be JavaScript Node can also load, so the module can never be `.ts`; `@meshfw/compiler` exports `./extensions` (the extension list) for the build script, so installing does not load the whole compiler. The manifest also sets `mxConfigTags: false` (Mesh files take nothing from the project's `mx.tags` or `mx.contracts`), `tagDirs: []` (MX's generic `tags/` directory is closed to them) and `reservedTags` (every key of `MESH_CONTRACTS`, so a project definition of one is `MESH_RESERVED_TAG`; `test/dialect-registration.test.ts` fails when the list and the contracts differ). Concepts (ADR-0085) will need a declared `tagDirs` entry later. `bun install` at the repo root is all there is: no `bun link`, no token, no local MX checkout. `bun run verify` runs on GitHub Actions (`.github/workflows/verify.yml`) on every pull request and every push to `main`. To work against an unreleased MX commit, run `bun link` inside the MX checkout and temporarily point `packages/compiler`'s two `@mxlang` dependencies at `link:` (or at a `file:` path), then revert before committing; never commit a `link:` entry, and never run `bun link @mxlang/...` at the root, which writes a `link:` dependency into the root `package.json`.
- Jig: `@jig-lang/jig` is pinned exact (`1.0.1`, from npm) as a dependency of `@meshfw/compiler` only; `src/typescript/render.ts` is its one import site (a test enforces it; runtime, model, the CLI and generated code never import it). Jig's disk loader resolves `.edge` only, so Mesh reads each `*.ts.jig` file itself and renders with `await edge.renderRaw(contents, view, templatePath)` (`templatePath` is only what errors name; do not use `renderRawSync`, whose wrapper has the wrong signature). `{{ }}` does not escape, and the final newline is dropped (Prettier restores it). A Jig error is `MESH_TEMPLATE_RENDER` at the template's line and column. Jig has no strict mode and loops over `undefined` as over `[]`, so `render.ts` registers Jig's `@each` tag again with one extra statement (the `meshLoopable` macro) that throws when the list is `undefined`: a project template that loops over a view field the view no longer has is a `MESH_TEMPLATE_RENDER` at the loop, naming the field (`null` and `[]` still loop zero times; a loop inside an `@if` that guards it is never reached).
- The MX packages are consumed from their published `dist` directories. `Cannot find module '@mxlang/core'` after a successful install means the installed version is broken or the scope entry was lost; check `bun.lock` for the `@mxlang` entries. Never build inside the MX checkout yourself.
- `bun run verify` runs every workspace package's `test`, `typecheck`, `build`, `validate` and `conformance` scripts (only `examples/hyper` has `conformance`; plus a type check for `scripts/`), including the docs build/link check, the blog generated-tree guard and generated-file type check, and compiler tests for the MX import boundary and complete MX fenced samples in `apps/docs/docs/docs/*.md` plus ADR-0050's reference. The Docs pages write **syntax v4** (`entity :Todo`, `belongs-to :list entity=List`, `input` with `&title`, `set` with `&done=true`). Docs checks report entity files checked and findings. Docs fences parse as authored through `parseEntitySource`; no normalisation or relaxed contracts. Before parsing, `checkDocsSyntaxV4` and `oldSpellingInV4` reject obsolete spellings, undeclared member heads, unimported entity identifiers and `self.` without destructured self parameters in that function; misplaced member lines and input assignments are parse errors. This is a bounded text guard, not full contract/type checking; planted tests pin those failures. `apps/docs/plugins/mx-highlight.js` carries one counted allowance, `MX_V4_INPUT_PENDING_SYNTAX_TABLE`: alpha.2 treats `input` as an HTML void tag, so nested input sections and bare member lines get same-width stand-ins for highlighting only. Rendering always uses authored text. MX owns the permanent fix (`mesh-syntax-highlighting-route`); both highlighter allowances stay until `@mxlang/tree-sitter-mx` moves past alpha.2, even though the parser pin no longer needs bridging. Other grammar errors still fail the build. Verification exits non-zero and names the failed step. The full Todo copies (Introduction, Tutorial and Entities) are byte-identical after stripping figure annotations; the home is a deliberate shorter excerpt whose shared lines must match. Quick start now runs the starter's single List entity and contains no MX fence. `apps/docs` also type-checks every TypeScript sample on the Docs pages against `apps/docs/samples/mesh-api.d.ts`, the declarations of the proposed API; a fence titled `(excerpt)` is skipped. `bun run test` and `bun run typecheck` run one kind only; `verify` runs in the pre-merge gate and CI (see the next item), not as a habit.
- `bun run test:affected` runs only the tests a change affects (operator order, 2026-10-18: agents run `test:affected` or `bun test <files>`, never the full suite; the full suite runs only in the pre-merge gate and CI). `scripts/test-affected.ts` takes the files changed against a base (default `origin/main`; `--base <ref>` overrides; uncommitted and untracked files count), maps each to its workspace package (`packages/*`, `apps/*`, `examples/*`) and adds every workspace package that depends on a changed one, transitively (`@meshfw/model` is not a dependency of `@meshfw/runtime`, so a model change does not run the runtime's tests), then runs each selected package's own `test` script one at a time (the examples' `mesh build --check` pre-step included) and exits non-zero if any fails. A package whose changed files are all test files runs only those files, through the package's own script when its final command is a bare `bun test` and as the full `test` script otherwise (a directory filter like `bun test test/` cannot be narrowed by appending a file); a package whose test-file changes are all deletions runs its full `test` script. A change outside every package, or in a package-shaped directory no manifest covers, that is not documentation (root `package.json`, `bun.lock`, root `tsconfig*.json`, `scripts/`, `.github/`) runs everything, the scripts' own tests included; a change only under `notes/` or to `*.md` outside `apps/docs` runs nothing and says so. The slow test files, 7 s or more on forge (`scripts/slow-tests.json`: `packages/compiler/test/expressions.test.ts`, `examples/hyper/test/daemon.test.ts`, `packages/cli/test/example-guard.test.ts`, `packages/data-sqlite/test/bus-conformance.test.ts`) are skipped unless `--slow` is passed or the file itself changed; the script prints what it skipped, and the skips reach `bun test` as appended `--path-ignore-patterns` flags (bun 1.4.2: the pattern is a glob matched against the path relative to the package cwd, like `test/framing*`, not a substring; a comma-separated list is one pattern, repeat the flag instead; `--pass-with-no-tests` covers a package whose only test files are slow). `--dry-run` prints the packages, files and reasons without running anything; `bun run test:fast` runs every package with the slow files skipped. The packages' own `test` scripts, `bun run test`, `bun run verify` and CI always run every file; the slow lane never changes what they run.
- With `meshfw` installed, run `mesh build`, `mesh build --check`, `mesh inspect [entity]`, `mesh export generators`, `mesh db push [--force]` or `mesh --help` from the project root containing `mesh.config.ts` (no upward search). ## Rules

- The user-facing CLI package is `meshfw` (binary `mesh`; it re-exports `defineConfig`, but projects import `defineConfig` from `@meshfw/runtime`); the starter is `create-meshfw` (`bun create meshfw todo-app`). Other framework packages remain `@meshfw/*`. These are the workspace package names and the documented 1.0 naming. User docs write `mesh build` and other `mesh` commands; Quick start alone explains the `bunx mesh build` local-binary alternative.
- User docs separate `configuration.md` (project/context/adapters/environment) from `command-line.md` (commands/flags/exit codes). `using-your-domain.md` replaces the old Calling actions page. Framework integration snippets are explicitly `(excerpt)` fences; the sample checker counts exclusions dynamically rather than claiming they compile.
- `plugins/mx-figure.js` also injects site title/heading CSS and strips paired code backticks from docmd's known plain-text title labels at build time. It must not rewrite authored code blocks, URLs or escaping. `apps/docs/test/browser/docs-structure.mjs` checks the sidebar/home link, heading scale and title labels in both themes; it needs `SHOTS_DIR`, `SITE_DIR` and `PLAYWRIGHT_MODULE` (Playwright Docker), separately from `verify`.
- `typescript` and `@types/bun` are declared only in the root `package.json`; packages do not repeat them.
- Use bun, never npm.
- Always write "Mesh" (never "Mash").
- Architecture docs hold what cannot be understood from a single code file.
- The `@mxlang` scope resolves from `https://npm.saulo.tech`, the operator's read-only npm registry (no uplink);
  `bunfig.toml` points only that scope at it. `@mxlang/tree-sitter-mx` is what the docs site highlights `mx`
  with; a docs fix goes in `apps/docs/plugins/mx-highlight.js` (the docmd plugin, the capture-name palette)
  or goes to the MX lead as a grammar gap.
- `apps/docs/plugins/mx-highlight.js` is MX's highlighter's docmd plugin and not ours to fork: the grammar
  and the queries belong to MX. Change the palette only, except for the explicitly approved, tested,
  counted v4 input allowance above and `MESH_V4_MEMBER_RENDER`: a Mesh-side render-only overlay
  that colours operand/bare/sort `&name` heads, and `%.now`/`%.today` where they start an operand (widened
  on the lead's brief), as `ts-member`, leaving literals, comments and infix operators (`a % b`) alone. Both bridges go away with `mesh-syntax-highlighting-route` (MX decision 182
  addendum 1). Do not patch the grammar or broaden either bridge silently.
- Home token explanations live in `apps/docs/plugins/mesh-home-hints.js`, wired by `mesh-home.js`.
  Keep descriptions outside the code so copying and the home-sample hash retain the authored file;
  every token in the fixed excerpt is checked against the commissioned wording. Each note has a shared
  family sentence followed by optional context; inline fragments use `mxHighlighter` at build time
  (TypeScript through its injection grammar), never a browser highlighter. Reference tokens name
  scoped targets for a single dashed SVG connector and outline. Keyboard navigation has one tab stop
  per nonblank line, with Left/Right and Home/End within it. Mutation/resize observers run only while
  a note is open; the panel is re-created after body replacement. Browser interactions and screenshots
  are exercised by `apps/docs/test/browser/home-hints.mjs` in Playwright's Docker image, separately
  from `bun run verify` (see the script header for its environment variables; screenshots default
  under `os.tmpdir()`, not the checkout).
- docmd 0.9.7 reads a raw HTML block until its tags balance, blank lines included, so Markdown (a fence
  above all) inside an open `<div>` is emitted as raw text. Wrap fences in a docmd container (`::: grids`)
  instead, and keep each HTML block self-contained. docmd also hides `<html>` until its theme script runs;
  `plugins/mx-figure.js` adds the `<noscript>` rule that keeps the site readable without JavaScript.
