# Roadmap

Date: 2026-10-10. This is revision 5 of the implementation plan. It re-cuts M3 onward of revision 4 (2026-10-05) around one ruling: Mesh 1.0 is done when the Hyper engine can be ported to Mesh. The section "Changelog" says what moved and why. Revision 4 and revision 3 (2026-10-04) are in this page's history; [plan revision 2 (superseded)](./plan-revision-2.md) is kept as a page.

## 0. What this page is

**Mesh** is a TypeScript framework modelled on Ash, the declarative framework for Elixir. One *entity file* declares a piece of data, the operations on it and the rules around them; Mesh derives types, input validators, action functions and the database schema from that file. This page says in what order Mesh is built. Each decision it rests on has its own decision record, listed in [decision records](../decisions/index.md) and cited as "[ADR-0050](../decisions/0050-entity-file-syntax.md)".

**Hyper** is a work tracker for people and AI agents, a separate project whose engine is an Elixir program on Ash and Postgres: 18 resources, 38 custom modules, 57 named rules, a write pipeline, an RPC transport, plugins and an export format (8,996 lines in 137 files). On 2026-10-07 the operator (the project owner, Saulo Vallory) ruled that **Mesh 1.0 is done when the Hyper engine can be ported to Mesh** (MX decision 185). Revision 4 predates that ruling: it ranks work by what a framework should have, and it ends v1 at M9 (migrations and Postgres). This revision ranks every feature by one question: **does the Hyper port need it?** What the port needs lands as early as it can. What it does not need moves after 1.0, and section 6 says so, with the evidence for each item. The evidence for the ranking is the [Hyper gap analysis](../research/hyper-port-gap-analysis.md), which maps every Hyper resource, rule, module and runtime feature to a Mesh construct and a milestone; codes such as [G05](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone) below refer to its section 4.

**What "done" means (the port gate, HP).** Hyper built on Mesh passes the conformance suite of the Hyper specification: `PROTOCOL.md` v0 and 126 black-box cases (`conformance/01..10-*.test.ts`) on the `feat/protocol-phases` branch (commit `ccc00f9`) of the Hyper specification repository (`svallory/hyper-engine-spec`, private), which drive any engine over a Unix socket. The port follows that specification and nothing else, and runs on SQLite. The engine's own v2 (HTTP, Postgres) replaced the specification's wire and does not pass the suite; it is not the target. [ADR-0072](../decisions/0072-mesh-1-0-is-the-port-gate.md) records the choice, and section 5 (HP) defines the gate.

**Where things stand (2026-10-10).** M0 and M1 are done, the move to the documented names is done (PR #47, PR #48, 2026-10-09), and so are the MX lowering of the `&` member positions (PR #50) and the Jig port (PR #51). M2 is done: the data layer in PR #53 (`@meshfw/data-drizzle`, `@meshfw/data-sqlite`, the `schema.ts` generator, `mesh db push`) and the generated action functions, `.mesh/index.ts` and the blog walking skeleton in [PR #54](https://github.com/svallory/mesh/pull/54). On `main` a generated action creates, updates and destroys rows, applies a constant `set`, validates input, and runs on SQLite. It runs nothing else: checks, non-constant `set`, `run`, policies and every `filter` or `sort` are listed in a "Not run in this version" comment (`packages/compiler/src/views/actions.ts:126-162`). Of Hyper's 57 rules, none runs today.

Terms:

- **MX** is a separate project that parses Marko-syntax files. Mesh calls `parseData` from `@mxlang/data`, which returns a static tree of tags and attributes plus diagnostics; nothing in the file is executed (MX notes, getting-started section 1). A **tag contract** tells MX which attributes, children and parents a tag allows. MX is core ([ADR-0043](../decisions/0043-mx-is-core.md)).
- An **entity file** is a `.mesh.mx` file under `src/domain/<module>/` ([ADR-0051](../decisions/0051-mesh-mx-files-and-the-mesh-host.md), [ADR-0057](../decisions/0057-one-domain-modules-as-folders.md)). Every declaration in it is `kind :name options` (entity file syntax v4, [ADR-0050](../decisions/0050-entity-file-syntax.md), [ADR-0066](../decisions/0066-names-and-references-are-atoms.md), [ADR-0067](../decisions/0067-members-imports-input-static-files.md)). The folder under `src/domain/` is the entity's **module**.
- **Core, adapter, extension** are the three rings ([ADR-0001](../decisions/0001-three-rings.md)). Core is what Mesh cannot work without. An adapter is one replaceable implementation of a contract core owns. An extension is an optional feature built on core's extension points.
- An **action** is one named operation on an entity (create, read, update, destroy). It is a generated TypeScript function, and calling it is the whole interface ([ADR-0005](../decisions/0005-core-interface-is-a-function-call.md)). A **transport** (command line, HTTP) is an optional adapter that calls it for an outside caller; none is built in 1.0, so the Hyper application writes its own socket server.
- A **cascade** is an action that writes other entities in its own transaction. A **seam** is a place in a generated action where the application may run code: before the transaction opens, inside it after each write, after it commits ([ADR-0075](../decisions/0075-seams-use-the-extension-hosts-names.md)).
- The **action context** is the second argument of every action: one flat object, typed `ActionContext` by the application, whose `actor` key is the one policies read and whose `system` key marks an internal write ([ADR-0059](../decisions/0059-action-context.md), [ADR-0071](../decisions/0071-system-key-on-the-action-context.md)). It is never ambient.
- A **capability** is an optional feature of a data adapter (joins, aggregates, upserts, atomic expressions), declared as static data so the build can check it.
- **Drizzle** is an established TypeScript query builder with SQLite and Postgres drivers; **drizzle-kit** generates SQL migrations from a Drizzle schema. Mesh's SQL adapters are built on both ([ADR-0014](../decisions/0014-sql-adapters-on-drizzle.md)).
- **Jig** is the operator's template engine for code generation; Mesh's emitters render through Jig templates ([ADR-0061](../decisions/0061-generators-are-jig-templates.md)).
- `verify` is the one script that runs every check, locally and on every pull request ([ADR-0031](../decisions/0031-no-ci-until-mx-is-published.md), amended 2026-10-05: the workflow `.github/workflows/verify.yml` runs it now that the `@mxlang` packages are installable from a registry).

## 1. Summary

1. **Mesh 1.0 needs six milestones after M2, not seven**: M3 data layer, M4 expressions (in memory), M7 relationships (the part Hyper uses), M5 action lifecycle with action composition, M6 lifecycle seams, M8 policies. Then the gate. Postgres (M9), SQL translation of expressions (M10) and the extension host (M11) are after 1.0 ([ADR-0072](../decisions/0072-mesh-1-0-is-the-port-gate.md)).
2. **The critical path is M3, M4, M7, M5, then M6 and M8 in parallel, then the gate.** Milestone numbers keep revision 4's names; the order changed. M7 moves ahead of M5 because the rules and policies M5 and M8 run read related rows.
3. **Three features are new, because the port cannot route around them**: an action that writes other entities in its own transaction ([ADR-0068](../decisions/0068-actions-compose-through-actions-and-tx.md), [G05](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), the largest gap); lifecycle seams, which carry the event log, the plugin hook and the broadcast ([ADR-0075](../decisions/0075-seams-use-the-extension-hosts-names.md)); and a `json` attribute type ([ADR-0069](../decisions/0069-json-attribute-type.md)). A small vocabulary addition, `via=` on a `has-many`, and one reserved context key, `system`, come with them ([ADR-0070](../decisions/0070-has-many-via.md), [ADR-0071](../decisions/0071-system-key-on-the-action-context.md)).
4. **Plain code first, declarative later.** Hyper's rules read other rows, walk trees and count filtered sets. Mesh has no filtered relationships, no unrelated reads and no recursion in its expressions. With action composition, those rules become plain-code `check`s over a transaction handle: less declarative than Hyper, and done earlier. Filtered relationships, identities and the SQL half of expressions come after 1.0.
5. **The Hyper application is Mesh-team work and starts now**, in `examples/hyper`, beside the milestones. Its socket server, idempotency store, event stream, sweeper, bootstrap and plugin host need only the M2 functions (about 2,400 of Hyper's 8,996 lines). When it passes the suite it moves to its own repository.
6. **The gate runs in `bun run verify`**, because the application lives in the workspace.
7. **After 1.0, in no fixed order**: Postgres and migrations, SQL translation and atomic updates, the extension host with named reusable checks, filtered relationships, identities, state machines, tracing, `on:load`, bulk actions, the agent surface and the rest of section 6.
8. **Bun only** ([ADR-0025](../decisions/0025-bun-only.md)), **established tools first** ([ADR-0030](../decisions/0030-established-tools-first.md)), **`verify` runs on every pull request** ([ADR-0031](../decisions/0031-no-ci-until-mx-is-published.md)).
9. **User docs first.** Behaviour is written on a Docs page, in the voice of a released product, before it is built; code follows the page or changes it in the same pull request ([ADR-0063](../decisions/0063-user-docs-first-and-the-hold.md)). The pages describe the target Mesh and the roadmap gives the timing: a construct that is documented but not built fails with the not-implemented error, which names its milestone ([ADR-0018](../decisions/0018-not-implemented-is-a-build-error.md)). Revision 5 removed nothing from the pages and added the pages for the new constructs.
10. **The vocabulary is Mesh's own**, informed by Ash, always in MX concise syntax ([ADR-0049](../decisions/0049-vocabulary-is-meshs-own.md), [ADR-0041](../decisions/0041-mx-concise-syntax.md)). The [Ash-to-Mesh mapping](./vocabulary-mapping.md) says where each Ash concept went.
11. **Mesh is open source under the MIT licence** and its docs are public ([ADR-0042](../decisions/0042-open-source-mit.md)).

## 2. Principles every milestone is checked against

Revision 4's nine principles stand. Revision 5 changes the emphasis of two and adds three.

1. **Generated code carries the behaviour; the run-time library stays thin** (Ruling 2; [ADR-0003](../decisions/0003-generated-code-carries-behaviour.md)). Test: the run-time library never reads the model. Ash keeps behaviour in the library, so stack traces are unhelpful and coverage of a user's own resource reads 0% (Synthesis section 6, item 2). A cascade is written out in the generated action: the `run` body calls the same generated functions a user would.
2. **No silent fallback.** A capability the adapter lacks, a tag the compiler does not implement yet, an expression that cannot be translated: each is a build error naming file, line and fix (Ruling 4; Synthesis section 8, "Silent fallbacks"). **This is why SQL translation can wait:** until M10, a declared `filter` or `sort` on a read, and a policy that reads the record on a read, are a build or run-time error that names the milestone, never an in-memory scan. The port uses the caller's plain-data `filter` instead (M3).
3. **Conservative defaults**: accept only listed inputs; required unless `nullable`; forbidden unless a policy allows, including an entity with no policies ([ADR-0055](../decisions/0055-policies-are-core.md)).
4. **"It was in the plan" is never a reason to hardcode something** ([ADR-0001](../decisions/0001-three-rings.md)). Every package states why it sits in its ring.
5. **One way to write each thing, few rules to remember** ([ADR-0050](../decisions/0050-entity-file-syntax.md)). Every vocabulary addition follows the `kind :name options` shape and the PR #1 pattern: one closed contract per tag, one negative fixture per rule with exact message, line and column. Examples are in MX concise syntax.
6. **The committed generated tree is guarded**: `verify` regenerates `.mesh/` and fails on any difference (Synthesis section 16, stage 8).
7. **Established tools first** ([ADR-0030](../decisions/0030-established-tools-first.md)): before building anything, look for a well-established tool and put it behind a Mesh contract.
8. **No application concerns in core.** How a caller is identified, how a program is exposed, login: the application's business, carried in its own `ActionContext` keys. Core takes an action context and runs an action.
9. **Docs first, then code** ([ADR-0063](../decisions/0063-user-docs-first-and-the-hold.md)). A milestone that adds behaviour updates its Docs page; one that adds a contract, a pipeline stage or a cross-package rule updates its Architecture page, in the same pull request.
10. **Ranked by the port.** A feature is on the path if a Hyper rule, action or protocol step needs it; otherwise it is after 1.0, however good it is (MX decision 185). The summary table of the gap analysis is the ranking.
11. **Plain code is a first-class answer** when the declarative form is not built. The entity file declares what it can, and the rest is a `run` or a `check` with a function body ([ADR-0053](../decisions/0053-validate-then-do.md), [ADR-0068](../decisions/0068-actions-compose-through-actions-and-tx.md)).
12. **A diagnostic that is a milestone limit says so.** Today `Create action :acquire of :Claim cannot fill fence` is a limit of M5, not a mistake in the file ([gap analysis, D04](../research/hyper-port-gap-analysis.md#52-the-diagnostics)). The not-implemented rule ([ADR-0018](../decisions/0018-not-implemented-is-a-build-error.md)) applies to it.

## 3. Packages

A bun workspace in `svallory/mesh`. Packages are published as `@meshfw/*`, the CLI package is `meshfw` and the command is `mesh` ([ADR-0060](../decisions/0060-meshfw-package-scope.md)); the workspace packages on `main` carry those names since PR #48.

```
apps/docs/            the docs site (docmd): Docs for users, Architecture for contributors
packages/
  model/              core       plain-data entity model, vocabulary registries, diagnostics
  compiler/           core       build pipeline (loads .mesh.mx through MX), tag contracts, emitter views and Jig templates, policy verifier
  runtime/            core       thin run-time library: ActionContext, errors, contracts, seams, policy engine, expression functions
  cli/                core       the `mesh` command (build, check, inspect, explain, export generators); adapters add commands
  data-drizzle/       adapter    shared code of the SQL adapters: Mesh queries and expressions -> Drizzle
  data-sqlite/        adapter    data layer on SQLite (file or in-memory), on Drizzle
examples/blog/        the example entities and a script that calls them
examples/hyper/       the Hyper application on Mesh; the port gate (moves to its own repository once it passes)

after 1.0:
  data-postgres/      adapter    data layer on Postgres, on Drizzle
  mx-host/            core       the MX host package named `mesh` (after MX decision 148)
  the extension host, inside compiler/ and runtime/
```

| Package | Ring | Why there |
|---|---|---|
| `model` | core, build time | Every build-time package reads the model. Plain JSON-serialisable types, the registries (attribute types, which are also tag names; step kinds; expression functions), the diagnostic type. |
| `compiler` | core, build time | The build pipeline is what makes Mesh a framework (Synthesis section 16). Owns stage order and the emitters every project needs, each a typed view plus a Jig template. It is also where MX is used: MX is core ([ADR-0043](../decisions/0043-mx-is-core.md)), so the tag contracts and the load and check-structure stages live here. `compiler` depends on MX; `model` and `runtime` never import it. The extension host joins it after 1.0. |
| `cli` | core, build time | The `mesh` command is the only entry to the pipeline. It builds a project; it does not run an application's actions. Commands that belong to an adapter's tool (`db push`, `migrate`) are contributed by that adapter, so `cli` imports no query library. |
| `runtime` | core, run time | What generated code imports: the `ActionContext` type, error classes, the data-layer contract with the query and expression-tree types, the re-entrant transaction helper, the seam types, the policy engine's run-time half, and the in-memory implementations of the registered expression functions. Imports nothing from `model`, `compiler` or Drizzle. |
| `data-sqlite`, `data-drizzle` | adapter | A project picks its database; the contract is Mesh's own (Synthesis section 11), and the query library inside an adapter is that adapter's private choice, Drizzle ([ADR-0014](../decisions/0014-sql-adapters-on-drizzle.md)). Drizzle is imported only here and in the emitted schema. |
| `examples/hyper` | example | The Hyper application, written against the generated functions: transport, idempotency store, event mapping, plugin host, sweeper, bootstrap. It is the gate's subject, not a Mesh feature. |

Policies are core, not an extension: there is no `ext-policies` package ([ADR-0055](../decisions/0055-policies-are-core.md)). Adapter slots of the Synthesis ring table (section 15) with no package in 1.0: transport ([ADR-0005](../decisions/0005-core-interface-is-a-function-call.md)); tracer (after 1.0, [ADR-0072](../decisions/0072-mesh-1-0-is-the-port-gate.md)); runtime host (Bun only, [ADR-0025](../decisions/0025-bun-only.md)). The authoring syntax and the expression parser are MX's. The actor resolver is dropped ([ADR-0059](../decisions/0059-action-context.md)); the job runner comes with workflows after 1.0 ([ADR-0023](../decisions/0023-workflows-and-jobs-deferred.md)).

## 4. Order

```
M0 M1 Realignment Jig port M2          (done)
 └ M3 data layer v1, and the column types Hyper needs
     ├ M4 expressions, in memory
     │   └ M7 relationships and computed fields, the part Hyper uses
     │       └ M5 action lifecycle and action composition
     │           ├ M6 lifecycle seams ─────────────┐
     │           └ M8 policies ────────────────────┴─ HP the port gate (Mesh 1.0)
     └ (M7's loading half needs only M3; its computed fields need M4)
HA the Hyper application: examples/hyper, runs beside everything above, from today

after 1.0, in no fixed order:
  M9 Postgres and migrations     M10 SQL translation, atomic updates, filtered relationships
  M11 extension host             identities, upsert, state machines, shared checks, bulk
```

**Rules across tracks.** M7 needs M3 for loading and self-reference and M4 for computed fields; it comes before M5 because many of the 57 rules and the relationship policies read a related row (`&task.state`), a loaded has-many (`&children.every(...)`) or a rollup (`&task.maxFence`), and M5's and M8's acceptance tests run them. M6 needs M5's phase structure (it adds the seams to it). M8 needs M5 (policies run in the lifecycle's slots) and M7 (the relationship checks), not M6. The gate needs M5 to M8 and HA. A milestone that adds a data-layer capability implements it in SQLite, the only adapter until M9.

**Prerequisites that are decisions or outside work, not milestones.** M4 needs [ADR-0012](../decisions/0012-expression-semantics.md) ruled, for the in-memory semantics only, and it is ruled: option A (2026-10-10), Mesh defines each registered function and operator and follows SQL's three-valued null logic, so the in-memory form gives the answers the M10 SQL evaluator will give; a construct the registry does not define stays plain code with JavaScript semantics (see [ADR-0012](../decisions/0012-expression-semantics.md)).

Sizes: **S** one pull request; **M** two to four; **L** five or more, split into tasks by whoever leads it. Sizes are scope, not time.

## 5. Milestones and tasks

"Vocabulary" means tag names or attributes added to the entity-file language.

### M1 — Build skeleton: entity file to model to emitted types (M, done)

- **Status.** Done on 2026-10-04, in the vocabulary of that morning, which copied Ash's DSL ([ADR-0034](../decisions/0034-vocabulary-copies-ash-dsl.md), since superseded; renamed to the entity syntax by PR #47 and PR #48, 2026-10-09): the vocabulary alignment (PR #11, PR #13), load and model (PR #12, with the model package in PR #9), the emitters for `model.json` and types (PR #15), the `mesh` command with `build`, `build --check` and `inspect` (PR #16), and the blog example guarded by `verify` (PR #17).
- **What it did.** Build stages 1, 2, 3, 7 and 8 of Synthesis section 16 in their simplest form: `parseData` with the contracts imported directly, `structural: "reject"` and `unknownTags: "reject"`; one root tag per file; a plain-data model with source positions; duplicate-name, missing-primary-key and unknown-`accept` checks; `model.json` and a types file per entity, from templates through a pinned formatter, byte-for-byte deterministic; the guard; the not-implemented rule ([ADR-0018](../decisions/0018-not-implemented-is-a-build-error.md)); the MX import boundary.
- **Acceptance tests (as passed).** (1) A reduced example builds; emitted types pass `tsc --noEmit`. (2) Two builds give identical bytes. (3) A hand edit to a generated file fails `mesh build --check`, which names the file. (4) An empty file, two root tags in one file, a duplicate name and an unknown `accept` name each fail with the expected message and position. (5) The full fixture fails with the not-implemented error for its first unsupported tag. (6) The registry-against-contract drift test. (7) Every row of the [mapping page](./vocabulary-mapping.md) marked "on main" has a contract and a fixture that match it. (8) `@mxlang/*` is imported only by packages that declare tag contracts.
- **What changed later.** The realignment task rewrote the vocabulary, the configuration key and the output folder (PR #47, PR #48); tests 4, 5 and 7 keep their meaning with the new names. Test 7 reads the section 3 examples of the mapping page, now in the v4 spelling.

### M3 — Data layer v1, and the column types Hyper needs (L)

- **Goal.** Reads with plain-data filters, sort and paging; transactions that plain code can use; and every column type, key and write path Hyper stores. Hyper's 18 tables push and round-trip.
- **Hyper unlocks.** All 18 entities as stored data; every `list_*`, `get_*` and `list_events` read through the caller's filter (Hyper's `read` actions with arguments become `{ filter, sort, limit }`); `Workspace`, `Collaborator`, `Machine`, `EvidenceReference`, `Completion` and `Assignment` complete as CRUD.
- **What moved, and why.**
  - From revision 4's **M5**: the "read for update" call of the data layer contract. Hyper reloads the row under the lock before every rule (`pipeline/changes/write_pipeline.ex:125-144`); the contract has to carry it before M5 uses it.
  - From revision 4's **M7**: the `max` and `count` aggregates, unfiltered. The claim fence is the Task's highest fence plus one (`tasks/claim/changes/lease.ex:23-39`). Joins stay out ([M10](#6-after-10)).
  - New: a **re-entrant transaction** ([G05](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)). A nested call "is an error" in contract v0 (`packages/runtime/src/data-layer.ts`); a call made inside a transaction now joins it. M5's composition ([ADR-0068](../decisions/0068-actions-compose-through-actions-and-tx.md)) stands on this.
  - New: a **`json` attribute type** ([ADR-0069](../decisions/0069-json-attribute-type.md), [G10](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), for the six map and array attributes (`Submission.evidence`, `LateResult.evidence`, `Run.inputs`, `Run.outcome`, `Attempt.outcome`, `Event.changes`). A Zod validator, a SQLite text column, and `unknown` in TypeScript; typing the shape is not in scope. It is a core type because the extension host that would contribute it is after 1.0.
  - New: **time-ordered UUID keys** ([G01](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), by generating UUIDv7 for every `uuid` primary key. The cost is a different generator; no syntax changes.
  - New: **an `integer` primary key the data layer fills** ([G12](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)): the next integer, computed inside the write transaction, so the sequence is gap-free because the adapter runs one writer at a time. Hyper's `Event.seq` is exactly this (`pipeline/event.ex:77-100`). Today an integer key can be neither sent nor filled (gap analysis, D02 and D07).
  - Dropped to after 1.0: keyset pagination (revision 4 M3 test 4), the capability names for joins, upserts and atomic expressions beyond declaring them, a bounded write queue with a typed `BusyError` ([G16](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone); the spec's v0 has no busy error and applies writes one at a time), and a restore write for import ([G18](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone); v0's export is `not_implemented`).
- **In scope.** Revision 4's mandatory set (select, insert, update, delete, transactions, filters, sort, pagination as limit and offset); plain-data filters with `eq ne lt lte gt gte in nil and or`; the capability manifest as static data; the SQLite conformance suite, file and `:memory:`; plus the additions above.
- **Out of scope.** Joins, upserts, atomic expressions, Postgres, keyset pagination.
- **Packages.** `runtime`, `compiler`, `model` (core); `data-drizzle`, `data-sqlite` (adapters).
- **Acceptance tests.** (1) The 18 Hyper entity files build and `mesh db push` creates 18 tables; a row of each type round-trips through its generated functions. (2) A `json` attribute stores and returns an object and an array; an invalid shape fails at the validator. (3) 1,000 creates of an `integer`-keyed entity, with a rolled-back transaction every tenth, leave the keys 1 to the count with no gap. (4) A function called inside a running transaction joins it; a throw after the inner call rolls both back. (5) Ids from two creates in one millisecond sort in creation order. (6) `readTask({ filter: { parentId: { eq: id } }, sort: ["createdAt", "id"], limit: 10 })` returns the page Hyper's `list_tasks` returns. (7) The M2 import rule holds.
- **Risks.** A `json` column has no foreign keys and no checks; a wrong shape inside it is found at the validator, not the database. The `integer` key fill must be a contract capability, not SQLite behaviour, or M9 inherits a silent difference.

### M4 — Expressions, in memory first (M)

- **Goal.** A function in an entity file whose body is one expression (an arrow, or a method body that is a single `return`) becomes a tree that Mesh checks at build time and evaluates in memory; the registry is the one Hyper's rules need. The SQL evaluator is M10 ([ADR-0010](../decisions/0010-one-expression-tree-two-evaluators.md), [ADR-0056](../decisions/0056-translated-expressions-are-one-expression-arrows.md), [ADR-0072](../decisions/0072-mesh-1-0-is-the-port-gate.md)).
- **Hyper unlocks.** About 28 of the 57 rules are checks of the record or of a related record; they need this, M7 (related reads) and M5 (gap analysis, Appendix A). Version checks, `task.settled`, `claim.active`, `run.cancelable`, `invocation.cost-unknown`.
- **What moved, and why.**
  - **The SQL evaluator, the "translated or error" classification and the function tables run through SQL leave** for M10. Hyper's own SQL is a handful of `exists` calculations that its code already memoises for the claim path (`tasks/locked_task.ex`); its reads are served by the caller's filter (M3). This is the largest single saving of the revision. The classification remains a design ([ADR-0056](../decisions/0056-translated-expressions-are-one-expression-arrows.md)), and the in-memory half is built to it.
  - **The Greffon report** (revision 4 M4 test 7) moves to M10, where the translator is designed.
  - **The registry grows by what Hyper uses**: `now()` (25 uses in `lib/`, [G23](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), optional chaining and `??`, and the quantifiers `some`, `every`, `find`, `filter` and `length` on a loaded has-many ([G07](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)). In memory they are JavaScript.
- **In scope.** The expression tree and its registry (`runtime`, `model`); conversion from MX's Babel node to the tree (`compiler`); the in-memory form emitted as readable TypeScript; free-variable errors; an injectable clock for tests. [ADR-0012](../decisions/0012-expression-semantics.md) must be ruled first, for the in-memory semantics only.
- **Out of scope.** SQL, `translate-or-error` on a filter, a sort or a policy, relationship traversal in SQL, `mesh explain`'s write-strategy classification.
- **Packages.** `model`, `compiler`, `runtime`.
- **Acceptance tests.** (1) Every registered function and operator has a table of inputs and outputs, null cases included, run through the in-memory form. (2) A free variable fails the build at its node. (3) `&children.every((c) => c.state !== :open)` and `&claims.some(...)` evaluate on loaded rows. (4) `now()` is the injected clock inside a test. (5) A body with two statements is plain code and still builds. (6) A `filter` on a read still fails with a message that names M10, not a wrong result.
- **Risks.** A read action with a declared `filter` cannot run until M10. Hyper declares four (`Task :get`, `:list`, `:next`, `Event :read`); the port serves them with the caller's filter and the application. If that proves unacceptable, M10's first half moves in.

### M5 — Action lifecycle and action composition (L)

- **Goal.** The generated action runs `validate` and `do` as [ADR-0053](../decisions/0053-validate-then-do.md) says, and an action can write other entities in its own transaction. Every Hyper write path works except the event log, the plugin hook and policies.
- **Needs.** M4 and M7 (related reads, loading and rollups).
- **Hyper unlocks.** Task, Claim, Submission, Review, Completion, Assignment, Dependency and the rest as full behaviour: the 57 rules (33 declarable, 24 as plain code), the 13 cascades, the version bump and `expected-version`, the state transitions. Suite groups 03, 04, 05, 06 and 07 (versions), less their event and permission cases.
- **What moved, and why.**
  - **Dropped to after 1.0**: the atomic one-statement update ([ADR-0054](../decisions/0054-write-strategy-is-inferred.md)), which changes the atomic clause of Ruling 3 ([ADR-0017](../decisions/0017-atomic-by-default-and-classification.md)) and the user docs' "One statement or two" paragraph ([ADR-0072](../decisions/0072-mesh-1-0-is-the-port-gate.md)). Hyper serialises writers and reloads under the lock, so every update is read-then-write, which the single SQLite writer makes correct. `mesh explain` prints that fact for each action.
  - **Dropped to after 1.0**: the eight OpenTelemetry spans ([ADR-0029](../decisions/0029-tracing-opentelemetry-api.md); Hyper has none), and with them the `@opentelemetry/api` dependency ([ADR-0062](../decisions/0062-direct-dependencies-zod-drizzle-opentelemetry.md)); `lock`, `relate` and `after-commit` as vocabulary.
  - **New: action composition** ([ADR-0068](../decisions/0068-actions-compose-through-actions-and-tx.md); [G05](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), [G06](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), [G36](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)). A `run` body, and a `check`, `when` or `set` value written as a function, receive `actions` (the generated functions, bound to the running transaction) and `tx` (reads). A call joins the caller's transaction (M3), carries the caller's context, and is checked by the called action's own policies.
  - **New: a step after the write.** Hyper's cascades run after the row is written, so that the command's own event comes before the nested ones (PROTOCOL section 6.1 fixes the event order, and suite group 08 asserts it for `review.accept` and `task.complete`). A `run` step takes `after=:write` (an atom, so it stays a fixed-set value). Steps without it run before the write, as in revision 4.
  - **New: `set` accepts a relationship** ([G30](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)): `&creator=({ actor }) => actor.id`. Today it is a build error and Hyper has 17 `relate_actor` uses. The docs already show recording the actor in a plain attribute; the new part is keeping the `belongs-to` and its loading.
  - **New: a create fills a required attribute from a non-constant `set`**, and a **destroy accepts `input`**. Both are documented already ([input](../../docs/entities.md#input), [destroy](../../docs/using-your-domain.md#destroy)); the code refuses them (gap analysis, D04 and D05).
  - **New: `details` on a `check`** ([G22](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), a function returning data, carried on the `InvalidInputError` issue. Hyper's `claim.task-ready` returns `{derivedState, reasons}`, `claim.current-fence` returns `{currentFence, stale}`.
  - **New: an application-level transaction** ([G05](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), [G25](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), for results that are not the record. The spec's v0 requires `warnings` on `task.complete` and `review.accept` (PROTOCOL section 9) and `outcome: "late-result-recorded"` on a submit or complete with a fence the actor held that has expired or been revoked (it succeeds and commits only `claim.late-result-recorded`). A generated action whose check fails cannot do that. So the application's method handler opens `transaction` (exported from `#mesh`), reads, chooses between the generated actions and `recordLateResult`, and adds `warnings` or `outcome` to its own result. It is application code over M3 and M5 and adds no construct.
  - **New: `before` in `validate`** ([G35](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), the stored record, beside `self` (the record with the inputs applied). Seven Hyper rules compare a new value with the stored one.
- **In scope.** Revision 4's phases, `validate` with `check`, `do` with `set`, `when`, `load`, `run`; `always`; typed arguments; the authorizer slot (still empty until M8); the error hierarchy with positions; `explain` for the plan; plus the additions above. Version bump and `expected-version` stay as a documented recipe (a `check` and a `set`), not a construct ([G02](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)).
- **Out of scope.** Atomic updates, tracing, bulk, `lock`, `relate`, `after-commit`, reusable steps, policies (M8), the seams (M6).
- **Packages.** `compiler`, `runtime`, `model` (core); `data-sqlite`.
- **Acceptance tests.** (1) `Task :complete` by the reviewer creates a Completion, settles the actor's pending Submission as accepted and releases the actor's Claim, in one transaction; a throw in the last step leaves no row of the three. (2) `Task :cancel` revokes the Task's claims, withdraws its pending Submission and cancels its running Runs. (3) `Claim :acquire` on an unassigned Task also creates an Assignment, and two concurrent acquires of one Task give one winner and one `claim.task-ready`. (4) Every failing rule of an action is reported together, with Hyper's names as `code`: `task.open`, `claim.current-fence` with `details.stale`. (5) A required attribute filled by a `set` arrow builds on a create; so does a `destroy` with an `input` argument. (6) A step with `after=:write` runs after the row is written and sees the stored record. (7) A relationship `set` from `actor.id` stores the key. (8) A second update with a stale `expectedVersion` gets `expected-version` and changes nothing. (9) The 57 rules of Hyper, each with a passing and a failing case, run through the generated actions (the cases that need neither events, policies nor plugins). (10) The application-level `transaction` returns `warnings` on a completion that has open prerequisites, and records a late result instead of failing on an expired fence.
- **Risks.** The widest milestone, and the one that decides whether plain code is acceptable. Principle 1 is tested hardest here: a cascade written out per action is long. A repeated cascade (the "release the actor's claim" step appears in three actions) becomes a small pure helper that takes values, never the model.

### M6 — Lifecycle seams (S to M)

- **Goal.** The application can run code at three named points of every generated action. These are the points Hyper's event log, idempotency record, plugin hook and broadcast stand on.
- **Needs.** M5's phase structure.
- **Hyper unlocks.** The typed event log and its ordering (suite group 08 and group 01's bootstrap events, PROTOCOL section 6.1), the idempotency record written in the command's transaction (group 07), `commandId` and `caller` on every event, after-commit delivery to subscribers (08.5 to 08.7), the `task.claim` hook (group 10).
- **What moved, and why.** This replaces most of revision 4's **M6** (the extension host). Revision 4's M6 is the widest milestone and its machinery (named phases, cross-extension write conflicts, composed contracts, attribute-type contributions, named reusable checks) serves a future the port does not reach. The port needs only the points an extension would use. Those points are built now for the application, with the names and payloads the host will use ([ADR-0075](../decisions/0075-seams-use-the-extension-hosts-names.md)); the host that lets an extension contribute them is M11, after 1.0.
- **In scope.**
  - *Seams* ([G11](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), [G12](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), [G13](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone), [G31](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)), registered when the application binds a data layer (`bind(layer, { seams })`, and `connect()` reading them from `mesh.config.ts`):
    1. `beforeTransaction({ entity, action, input, context })`: before the transaction opens; may throw to refuse. Hyper's plugin hook at `task.claim` ([ADR-0073](../decisions/0073-plugins-follow-the-specs-single-hook.md)).
    2. `afterWrite(db, { entity, action, before, after, input, context })`: inside the transaction, immediately after each row is written, before any `after=:write` step; may write through `db`, the transaction's data operations (not the read handle `tx` of M5). Hyper's event append (`write_pipeline.ex:150-160`) and the idempotency record.
    3. `afterCommit({ changes })`: once, after the outermost transaction commits, with the list of every row written in it, in order. Hyper's PubSub broadcast. Not called on rollback.
  - A nested call runs the seams of its own row writes; the seam's context carries the caller's `context`, so `caller` and `commandId` reach every event (`write_pipeline.ex:162-174`).
- **Out of scope.** Loading seams from extensions; named phases and conflict detection; a plugin host (the application writes it); a transport; an action manifest for generic dispatch (the spec's v0 dispatches a fixed method table that the application writes once).
- **Packages.** `compiler`, `runtime` (core).
- **Acceptance tests.** (1) A write to any of the 18 entities calls `afterWrite` once with the right `before` and `after`; a read does not. (2) For `Review :accept`, the seam sees `review.accept` before `task.complete`, `submission.settle` and `completion.record`. (3) A throw in `afterWrite` rolls back the whole action. (4) `afterCommit` is not called when the transaction rolls back, and is called once with every change when it commits. (5) `beforeTransaction` that throws writes nothing. (6) `commandId` and `caller` from the context are on the seam's input in a nested call. (7) The M2 import rule covers the seam types in `runtime`.
- **Risks.** A seam is a second extension surface beside the host that comes later; keep the three points few and their payloads plain data, so M11 can wrap them rather than replace them. `afterWrite` always receives `before`; that is free while every update reads first (M5), and it would force a read first on each update once M10 brings atomic updates back, cancelling their point. Make `before` lazy or opt-in then. Under the spec's v0 the events are typed domain events with payloads ([gap analysis, section 3.2](../research/hyper-port-gap-analysis.md#32-the-same-features-against-the-specs-v0-protocol)), so the application's table from (entity, action) to event type sits on this seam; the seam itself stays generic.

### M7 — Relationships, the part Hyper uses (M; before M5)

- **Needs.** M3 for loading; M4 for computed bodies.
- **Goal.** Entities load their related rows; an entity can relate to itself; computed fields and rollups run in memory. Hyper's derived state and the ready test work.
- **Hyper unlocks.** `Task` derived state, `blocked`, the quantified rules (`task.children-settled`, `claim.task-ready`), `Task :next` as application code over a list, `Run` and `Invocation` with their parent links, `Collaborator.memberships`. Part of suite groups 05 (claims) and 03 (tasks).
- **What moved, and why.**
  - **In**: relationships to the entity's own type ([G28](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone); today it needs a self-import); and `via=:dependent` on a `has-many`, an atom naming the other entity's `belongs-to`, for entities that hold several keys back (Membership has three to Collaborator, Dependency two to Task) ([ADR-0070](../decisions/0070-has-many-via.md)).
  - **In**: `load` of a relationship and of a computed field; rollups `count` and `max` (`max :maxFence of="claims.fence"`), and `max` over a `timestamp`. **Rollups have one home**: M3 supplies the `max` and `count` primitives in the data layer, and M7 evaluates a rollup by calling them. A rollup is therefore not translated into a SQL join until M10, and is not filterable or sortable until then. The user docs keep describing the SQL rollup as the target; until M10, filtering or sorting by a rollup fails with the not-implemented error naming M10.
  - **Out, to after 1.0**: joins and aggregates as SQL capabilities, `sum`, `avg`, `min` rollups, filtered relationships and filtered aggregates, `on:load` ([ADR-0052](../decisions/0052-actions-auto-and-on-load.md); a relationship loads through the auto read), the policy-aware read of a related entity, generated path types, the unique index of a `has-one` ([ADR-0045](../decisions/0045-has-one-uniqueness.md)), cross-file inverse checks. Hyper's filtered relationships (`current_assignment`, `active_claim`, `pending_submission`) are written as `.some(...)` and `.find(...)` over the unfiltered `has-many`, in memory.
- **In scope.** `belongs-to`, `has-many`, `has-one` with loading by a second query; key columns as on main; self-reference; `via`; the loading half of the `load` step (the step itself runs in M5); `count` and `max`; computed fields with bodies, in memory; the type-level rule that an unloaded relationship is a type error.
- **Out of scope.** As above.
- **Packages.** `model`, `compiler` (core); `data-drizzle`, `data-sqlite`.
- **Acceptance tests.** (1) `Task.parent`, `Task.children`, `Run.parentRun` and `Invocation.corrects` build with no self-import and load. (2) `Collaborator.memberships via=:collaborator` follows `collaboratorId`, not `grantedById`; without `via` the build lists the candidates. (3) `maxFence` over claims returns the highest fence. (4) `derivedState` on a Task returns `done`, `canceled`, `in-review`, `claimed`, `blocked` or `ready` as Hyper's `DerivedState` does for the same rows (`tasks/task/calculations/derived_state.ex:10-25`). (5) Reading an unloaded relationship is a type error; a load that cannot be served is a run-time error. (6) A relationship to an unknown entity fails at the tag.
- **Risks.** A computed field that loads rows per record is an N+1 in memory. Hyper's `LockedTask` exists to avoid exactly that for the claim path; measure `Claim :acquire` here first.

### M8 — Policies, in core (M)

- **Goal.** Authorization as declared data in the entity file ([ADR-0022](../decisions/0022-policies-simple-tier-as-extension.md), [ADR-0055](../decisions/0055-policies-are-core.md)); deny by default from here on. Hyper's roles and relationship checks as policies.
- **Needs.** M5 and M7.
- **Hyper unlocks.** Suite group 02 (permissions); the 29 `Role` checks and the six relationship checks (`Manager`, `Assignee`, `Revoker`, `Reviewer`, `Reporter`, `Role self:`).
- **What moved, and why.**
  - **In**: policies as documented: `policy #name` with `types=[...]`, `actions=[...]` or neither; `authorize-if` and `forbid-if` combined without order; every covering policy must pass; an action no policy covers is forbidden, with an error naming the entity and how to write an open policy; no `bypass`. A check that needs no stored record is evaluated once before the transaction; a record-reading check on a write is evaluated in memory on the locked row (`ForbiddenError` with `breakdown`). **Read policies are query filters**, as ADR-0022, ADR-0055 and the lifecycle page say: a row the caller may not see is not found, and an actor-only read policy such as `isMember(actor)` is a bound value that leaves a non-member an empty result, which is what Hyper's `Member` check does (`checks/member.ex:16-17`). A denied read is never `ForbiddenError`.
  - **In**: a write policy may read other entities through `tx` ([ADR-0074](../decisions/0074-write-policies-may-read-through-tx.md)), so the actor's role is read inside the transaction, as in Hyper, and cannot go stale between the read and the write.
  - **In**: a reserved **`system` key on `ActionContext`** ([ADR-0071](../decisions/0071-system-key-on-the-action-context.md), [G20](../research/hyper-port-gap-analysis.md#4-summary-features-who-needs-them-and-the-milestone)). There is still no `bypass` inside a policy ([ADR-0055](../decisions/0055-policies-are-core.md)): an internal write (bootstrap, the lease sweeper, a cascade through `actions`) carries `context.system`, and the write policies of internal-only actions and the role policies admit it through `isSystem(context)`. The human `actor` stays on nested calls, so events keep Hyper's `actor_id`. The application sets the key, never from input.
  - **Out, to M10 or after 1.0**: folding a **record-reading read policy** into the query, which needs the SQL translator. Until M10 such a policy is a loud build or run-time error naming M10 (principle 2). Hyper has none: its read policy is membership only. Also out: the not-found outcome of a denied atomic write ([ADR-0046](../decisions/0046-denied-atomic-write-outcome.md)), `can` and its structured breakdown for a call, the policy formula kept for a solver.
- **In scope.** `policies` with `types`, `actions`, `when`, `authorize-if`, `forbid-if`; the verifier that every `actions=` names a real action; deny by default; nested calls checked against the nested action's policies; `ForbiddenError.breakdown` as data.
- **Out of scope.** As above; a solver; field policies; policy groups; access types.
- **Packages.** `compiler`, `runtime`.
- **Acceptance tests.** (1) A guest cannot create a Task; a member can; the error names the policy. (2) An action no policy covers is forbidden, and the error shows how to write an open one. (3) `Claim :acquire` on a Task assigned to someone else is forbidden to anyone but the assignee. (4) A non-member's `readTask` returns no rows and no error; a member's returns the rows. (5) An owner can revoke a claim; the delegator and the reviewer can; a member who is neither cannot; a membership revoked inside the same transaction is seen by the next write's policy. (6) A nested call from `Task :complete` into `Completion :record` passes because it carries `context.system`, and the written event's actor is still the human; the same direct call from a worker is forbidden. (7) Moving a policy, or a check inside one, changes no decision. (8) A policy whose `actions=` names a missing action fails the build. (9) A read policy that reads the record fails with the error that names M10.
- **Risks.** Every write policy of an internal-only action carries `|| isSystem(context)`. If that repeats too much, shared checks (after 1.0) are the fix, and not `bypass`. `system` is a flag any code holding the context can set; it is as trustworthy as the application that builds the context. Until M8 nothing restricts a caller; a project built on M2 to M7 must not be exposed.

### HA — The Hyper application (S to M, Mesh-team work in `examples/hyper`, starts now)

- **Goal.** The parts of Hyper that need nothing from Mesh beyond what M2 has, built so they are ready when M5 to M8 land. The application lives in `examples/hyper` until it passes the gate; then it moves to its own repository.
- **Contents** ([gap analysis, section 3](../research/hyper-port-gap-analysis.md#3-protocol-and-runtime-features-outside-the-resources)): the Unix-socket server and its envelope (newline-delimited JSON-RPC 2.0, the spec's v0); the method table from methods to generated functions; the idempotency store (written in the command's transaction, so after M6); the lease sweeper; bootstrap; configuration through `context`. Then, as M6 lands, the event mapping and subscriptions and the plugin host ([ADR-0073](../decisions/0073-plugins-follow-the-specs-single-hook.md)).
- **Size.** About 2,400 of Hyper's 8,996 lines are this track, and none of it waits for M3.
- **Acceptance.** It builds and type-checks in `bun run verify` from the first pull request, and its conformance cases are added as the milestones that unlock them land.

### HP — The port gate: Mesh 1.0

- **Goal.** Mesh 1.0 is done when the Hyper engine can be ported to Mesh (MX decision 185; [ADR-0072](../decisions/0072-mesh-1-0-is-the-port-gate.md)).
- **Definition.** Hyper-on-Mesh passes the **specification's conformance suite**: the 126 `test(` cases of `conformance/01..10-*.test.ts` on the `feat/protocol-phases` branch of the Hyper specification repository, run as `ENGINE_CMD="bun examples/hyper/main.ts" bun test conformance`, strict schema validation on (its default). The groups: 01 bootstrap and transport, 02 permissions, 03 tasks, 04 dependencies and blocking, 05 claims, 06 review and completion, 07 idempotency and versions, 08 events and subscriptions, 09 scenarios, 10 plugins. The suite covers twelve entities; Run, Attempt, Invocation, Machine, SessionReference and workspace export and import are not in it and are ported after the gate.
- **Acceptance.** The suite is green in CI, inside `bun run verify`; no test is skipped; the lines Mesh could not express are in the entity files as `// GAP` comments, and the seven placeholder checks (`that=() => true`) that build green and hide a rule are counted at the gate review and accepted by the lead. How `verify` obtains the suite (a pinned checkout of the specification branch, or a vendored copy) is settled by the task that adds `examples/hyper`.

## 9. Risks

1. **The code and the docs differ by what is not built.** PR #47 and PR #48 (2026-10-09) moved the code to the documented names; the MX lowering (PR #50), the Jig port (PR #51) and M2 (PR #53, PR #54) followed. Every Architecture page that describes design the code does not implement says so in a callout; the Docs pages state the target. The Docs pages describe the target, so they also describe SQL translation, atomic updates, tracing, `on:load`, `can`, Postgres, migrations and extensions that ship after 1.0, and the new `actions`, `tx`, `after=:write`, `json`, `via=`, `system` and seams before any of them is built. Each fails with the not-implemented error naming its milestone until it ships. Two consequences to watch: the tutorial's declared `filter`/`sort` read and owner read policy do not run on Mesh 1.0 as scoped, and a denied write that reads the record reports `ForbiddenError` where the Docs say not found. Whether to pull a narrow SQL slice or `can` into 1.0 is open. The sample checks accept fences for constructs the contracts do not accept yet only as text.
2. **MX is pre-release** (MX notes, getting-started section 5). `packages/compiler` pins `@mxlang/core` and `@mxlang/data` to exact pre-release versions, so nothing resolves a range and a breaking change stops Mesh when the pin moves, not the day MX pushes.
3. **Drizzle v1 is a release candidate, its relations API is being replaced, drizzle-kit is mid-rewrite** (Synthesis section 12, risk 1; section 10). M2 uses the stable pair `drizzle-orm@0.45.3` / `drizzle-kit@0.31.11` ([ADR-0048](../decisions/0048-schema-inside-the-process-for-tests.md), [ADR-0062](../decisions/0062-direct-dependencies-zod-drizzle-opentelemetry.md)). Mitigation: exact pins; Drizzle imported only in `data-*`; an upgrade is its own pull request and must pass the suite; Mesh does not use the relations API.
4. **CI runs `verify` and nothing more** ([ADR-0031](../decisions/0031-no-ci-until-mx-is-published.md), amended 2026-10-05). A green run says the checks in `verify` passed, not that a change is correct; the review protocol still carries that. From the gate on, `verify` also runs the 126 conformance cases.
5. **The two-evaluator promise is half delivered at 1.0.** Only the in-memory evaluator exists; a declared `filter` or `sort` and a record-reading read policy fail loudly and name M10. The shared function tables ([ADR-0010](../decisions/0010-one-expression-tree-two-evaluators.md)) cover registered functions, not their combinations, once M10 adds the second evaluator.
6. **Thin engine against readable output.** If generated action functions become unreadable, the point of Ruling 2 is lost. M5 is the widest milestone and a cascade written out per action is long; watch it.
7. **No authorization until M8.** Milestones M2 to M7 produce runnable actions with no access control; this is stated in M2 and M8.
8. **Single-writer correctness is a hypothesis.** Hyper's concurrency tests were not run against a single SQLite writer. The suite's lease and race cases (groups 05, 07 and 10) are the first test of it; if they fail, M9 joins the critical path.
9. **`system` is a flag.** Any code that holds the context can set it ([ADR-0071](../decisions/0071-system-key-on-the-action-context.md)). A write policy that forgets the clause blocks an internal write, which is safe; a policy that admits `system` too widely is a review matter.
10. **Placeholder checks hide rules.** Seven rules Mesh cannot express are `that=() => true` in the entity drafts: they build green. The gate review counts them.
11. **Overridden templates fork** ([ADR-0061](../decisions/0061-generators-are-jig-templates.md)). A project that overrides a template stops receiving fixes to it, and the view types become a public contract.
